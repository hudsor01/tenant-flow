## Conflict resolved in this plan

`66-RESEARCH.md` §"Pattern 2: Token generation server-side" writes
`encode(digest(v_raw,'sha256'),'hex')` and `gen_random_bytes(32)` **unqualified** inside a
function with `set search_path = public`. That code would fail at runtime, not at
migration time. `66-CONTEXT.md` D-15 verified against production on 2026-08-06 that
pgcrypto is installed in the `extensions` schema and `digest` exists only there
(`digest_in_public = 0`). CONTEXT outranks RESEARCH, so both pgcrypto calls are
**schema-qualified** (`extensions.gen_random_bytes`, `extensions.digest`) while
`search_path` stays `public` per CLAUDE.md. `gen_random_uuid()` needs no qualification —
it is core PostgreSQL, not pgcrypto. Plan 66-06 smoke-calls this RPC against production
precisely because this is the one line that cannot be proven correct from the repo.

```sql
-- OWNER-GATED (grant execute to authenticated; each validates auth.uid() internally)

create_application_link(p_unit_id uuid, p_expires_days int default 60)
  returns table (link_id uuid, raw_token text, expires_at timestamptz)

revoke_application_link(p_link_id uuid)
  returns void

set_application_status(p_application_id uuid, p_status text,
                       p_disposition_reason text default null)
  returns void

set_application_notes(p_application_id uuid, p_notes text)
  returns void

record_application_conversion(p_application_id uuid, p_tenant_id uuid)
  returns table (success boolean, reason text)

-- SERVICE-ROLE ONLY (revoke from public; grant execute to service_role)

get_application_context(p_token_hash text)
  returns table (valid boolean, reason text, property_label text,
                 unit_label text, rent_amount numeric, owner_display_name text)

submit_rental_application(p_token_hash text, p_submission_id uuid,
                          p_payload jsonb, p_ip text, p_user_agent text)
  returns table (success boolean, reason text, application_id uuid)
```

**Reason codes** — one closed set, shared by the context and submit paths:
`invalid_token` | `expired_token` | `revoked_token` | `link_capped` | `rate_capped` |
`invalid_payload` | `duplicate`.

**Caps (D-04a / F-6):** lifetime `submission_count >= 250` → `link_capped`; rolling
1-hour count for the link `>= 25` → `rate_capped`. Both evaluated after the row is locked.

`create_application_link(p_unit_id uuid, p_expires_days int default 60)` —
`language plpgsql security definer set search_path = public`:
- `v_owner := (select auth.uid())`; raise if null.
- Raise `unit not found` unless a `public.units` row exists with that id AND
  `owner_user_id = v_owner`. Use the same message for "does not exist" and "not yours" —
  a distinct message enumerates other owners' unit ids.
- Refuse when an active link already exists for the unit: any row with that `unit_id`,
  `revoked_at is null` and `expires_at > now()` → raise `link already active`. The UI
  never offers Create while a link is active (§C), so this is the double-click and
  race guard, and it keeps "one active link per unit" true without a partial unique
  index (a `now()` predicate is not immutable and cannot be indexed).
- `v_raw := encode(extensions.gen_random_bytes(32), 'hex')` — 256 bits from the server's
  CSPRNG. Never `gen_random_uuid()` as a token (122 bits and structured), never client
  entropy, never a query parameter.
- Insert with `token_hash = encode(extensions.digest(v_raw, 'sha256'), 'hex')`,
  `raw_token = v_raw`, `expires_at = now() + make_interval(days => p_expires_days)`,
  `owner_user_id` and `created_by` both `v_owner`.
- Clamp `p_expires_days` into `[1, 365]` and comment why: an unbounded expiry is a
  permanent public write surface, and a zero/negative one mints a dead link.
- Return `link_id`, `raw_token`, `expires_at`.

`revoke_application_link(p_link_id uuid)` — same declaration form:
- Gate on `auth.uid()`; `update ... set revoked_at = now() where id = p_link_id and

  zero rows are affected — again, one message for both "missing" and "not yours".
- Revoking never touches applications already received (§C copy promises this).

Grants for both: `revoke all on function ... from public;` then
`grant execute on function ... to authenticated;`. Both gate on `auth.uid()` internally,
which is what makes the `authenticated` grant safe — the same posture as the 19 functions
in `20260529225039`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Edge Function (service_role) → database | The Edge Function holds the service-role key. These RPCs are where its authority is bounded — it can submit an application, and nothing else. |
| authenticated owner → their own rows | With no UPDATE policy on either table (plan 66-01), these RPCs are the entire owner write surface. |
| concurrent submissions → the same link | The reusable link means N applicants race the same row. This is where that race is resolved. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-66-05 | Denial of Service | application flood through the reusable link | mitigate | Lifetime cap 250 and rolling-hour cap 25, both evaluated after `select ... for update` on the link row. Same transaction as the insert, therefore fail-closed by construction (F-6). Upstash is the cheap outer layer, not the gate. |
