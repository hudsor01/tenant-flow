  <files>tests/integration/rls/rental-application-links.rls.test.ts</files>
  <read_first>
    - `tests/integration/rls/lease-signing-tokens.rls.test.ts` in full — the fixture/teardown strategy, the `sha256Hex` node-crypto helper, the deploy probe, and the grant-lockdown assertions using `REVOKED_CODES`
    - `tests/integration/rls/_helpers/revoked-codes.ts` — the set of PostgREST error codes that count as "denied"
    - `supabase/migrations/*_rental_application_rpcs.sql` — `create_application_link`, `revoke_application_link`
    - `66-CONTEXT.md` D-03, D-03a
  </read_first>
  <action>
Seed with the service-role client: a property and a unit owned by ownerA, plus a unit
owned by ownerB. Tear both down in `afterAll` regardless of test outcome.

Assertions:
1. **Token shape.** ownerA calls `create_application_link(unitA)`. The returned
   `raw_token` matches `/^[0-9a-f]{64}$/` — 32 bytes hex, 256 bits. Then read the row with
   the service-role client and assert `token_hash === createHash("sha256").update(raw_token).digest("hex")`.
   Recomputing the hash in Node is the assertion; reading the column back and comparing it
   to itself proves nothing.
2. **Re-copyability (D-03a).** Read the row a second time and assert `raw_token` is still
   populated and identical. This is the property `/sign` deliberately does not have, so a
   copy-paste of the `/sign` migration would fail here.
3. **Owner isolation, read.** ownerB selects `rental_application_links` and gets zero rows
   for ownerA's link. Assert on the row count for that specific id, not on an empty array
   — ownerB may legitimately have their own links.
4. **Owner isolation, write.** ownerB calls `create_application_link(unitA)` → rejected.
   ownerB calls `revoke_application_link(linkA)` → rejected. Assert the error message is
   the SAME as the message for a genuinely nonexistent id, so the RPC does not enumerate.
5. **No authenticated direct write.** ownerA attempts
   `.from("rental_application_links").insert({...})` and `.update({...})` and `.delete()`
   → each denied (accept any `REVOKED_CODES` shape or a zero-row result for
   update/delete). Plan 66-01 declares only a SELECT policy; this proves it.
6. **anon lockdown.** An `anon`-key client attempts a select and an insert on
   `rental_application_links` → both denied.
7. **Active-link refusal.** ownerA calls `create_application_link(unitA)` again while the
   first is active → rejected. Then revoke the first and call again → succeeds. This pair
   is what makes "one active link per unit" true without a partial unique index.
8. **Revoke is idempotent-safe.** Revoking an already-revoked link → rejected with the
   not-found message, and the original `revoked_at` is unchanged.
  </action>
  <verify>
    <automated>bun run test:integration -- --run tests/integration/rls/rental-application-links.rls.test.ts</automated>
  </verify>
  <acceptance_criteria>

    - Assertion 2 asserts `raw_token` survives a second read. A `/sign`-style shown-once implementation fails here — which is the point of D-03a.

  <read_first>

  <action>
Seed a property, unit, link and (for the conversion tests) a tenant, all owned by ownerA,
via the service-role client.

**Group A — the APPLY-02 invariant.** This is the group the requirement exists for.
1. `anon` client `.from("rental_applications").insert({...})` → denied.
2. `anon` client `.from("rental_applications").select()` → denied or zero rows.
3. `anon` client `.rpc("submit_rental_application", {...})` → denied.
4. `authenticated` (ownerA) `.rpc("submit_rental_application", {...})` → **denied**. The
   function is `service_role`-only; a signed-in user must not be able to inject
   applications against a link hash they can observe.
5. `authenticated` (ownerA) `.from("rental_applications").insert({...})` → denied. Plan
   66-01 declares no INSERT policy for any role.
6. `authenticated` (ownerA) `.from("rental_applications").update({ status: 'approved' })`
   → denied. No UPDATE policy exists; status changes are RPC-only.

**Group B — caps, under real concurrency.**
7. Service-role calls `submit_rental_application` in a loop until `submission_count`
   reaches the lifetime cap, then one more → `success: false, reason: 'link_capped'`.
8. **Concurrency.** With `submission_count` set one below the lifetime cap (set it
   directly with the service-role client to keep the test fast), fire N parallel
   `submit_rental_application` calls with `Promise.all` and distinct `submission_id`s.
   Assert **exactly one** succeeds and the rest return `link_capped`. Then assert
   `select count(*)` for that link increased by exactly one. A sequential-only test passes
   against a cap read outside the `FOR UPDATE` lock; this one does not.
9. Rolling-hour cap: insert 25 rows for the link with recent `created_at` via
   service-role, then submit → `rate_capped`.

**Group C — idempotency and payload.**
10. Two `submit_rental_application` calls with the SAME `submission_id` → both report
    success, exactly one row exists, and `submission_count` incremented by exactly one.
    Assert all three; the row count alone would pass against an implementation that
    increments twice and later mis-caps.
11. A payload missing a required key → `invalid_payload` and zero rows.
12. A payload carrying an `ssn` key: the RPC takes `p_payload jsonb` and does not
    enumerate keys, so assert the invariant that matters — **no column named `ssn` exists**
    (`select column_name from information_schema.columns where table_name='rental_applications'`
    contains none of `ssn`, `social_security`, `date_of_birth`, `government_id`,
    `bank_account`, `routing`) — and that the row written from a payload containing `ssn`
    stores it nowhere retrievable. State in a comment that key-level rejection is the Edge
    Function's job (plan 66-02's `parseSubmissionPayload`, unit-tested there) and that this
    assertion covers the storage layer.

**Group D — status and conversion.**
13. `set_application_status` to each of the four values by ownerA → succeeds; to
    `'nonsense'` → rejected.
14. `rejected` without a `disposition_reason` → rejected; with one → succeeds and
    `decided_at` is stamped.
15. Moving `approved` → `reviewing` → `approved` leaves the ORIGINAL `decided_at`
    (`coalesce`, never overwritten). Assert the timestamp equality explicitly — an
    overwrite silently extends PII retention past policy.
16. ownerB calling `set_application_status` on ownerA's application → rejected.
17. `record_application_conversion` sets `converted_tenant_id`, `converted_at` and
    `status='approved'`. A second call → `success:false, reason:'already_converted'` and
    the tenant id is unchanged.
18. `record_application_conversion` pointing at a tenant owned by ownerB → rejected.
19. **D-09, both directions.** Delete the tenant → the application still exists with
    `converted_tenant_id` null. Then delete the application → the (recreated) tenant still
    exists. Assert both rows by id after each delete.

**Group E — deployed-function boundary** (skip cleanly when the probe says undeployed).
20. POST to `/functions/v1/apply-token` with a filled `company_website` → HTTP 200
    `{"success":true}` **and** zero new rows for that link.
21. POST with `form_loaded_at = Date.now()` → HTTP 200 `{"success":true}` and zero new rows.
22. POST with a valid payload, honeypot empty and `form_loaded_at` 10s in the past →
    HTTP 200 `{"success":true}` and exactly one new row whose `applicant_email` is the
    lowercased submitted address. Delete it afterwards.

Tear everything down in `afterAll`.
  </action>

   other twenty leak.
2. **Stub retained.** The same row still has `unit_id`, `property_label`, `unit_label`,
   `status`, `created_at`, `decided_at`, `disposition_reason`, `occupant_count` intact,

3. **Converted rows skipped.** A row with `converted_tenant_id` set and `decided_at`
   backdated 800 days is NOT anonymized. Assert `anonymized_at is null` and
   `applicant_email` unchanged.
4. **Already-anonymized rows skipped.** Re-run the sweep and assert the first row's
   `anonymized_at` is unchanged (not re-stamped).
5. **In-window rows untouched.** A row backdated 700 days (inside the 730-day window) is
   not anonymized.
6. **`created_at` fallback.** A row with `decided_at` NULL and `created_at` backdated 800
   days IS anonymized — proving the `coalesce(decided_at, created_at)` clock.
7. **Config window honoured.** Temporarily set `app_config('applications.retention_days')`
   to `'1'`, insert a row decided 2 days ago, run the sweep, assert it was anonymized, then
   restore `'730'`. Use a `try/finally` so a failing assertion cannot leave production with
   a one-day retention window. Say that in a comment — this test can do real damage if it
   leaks its own state.
8. **Absent-config fallback.** Delete the config row, run the sweep against a 700-day row
   and an 800-day row, assert only the 800-day one was anonymized (default 730), then
   restore the row. Also in `try/finally`. This is the assertion that catches the NULL-window
   fail-open, where the interval is NULL and the sweep silently anonymizes nothing.
9. **No archive table exists.** `select count(*) from information_schema.tables where
   table_schema='public' and table_name like 'rental_application%archive%'` returns 0
   (D-11c). A schema-level assertion, so it cannot be satisfied by a code path.
10. **Cron registered and unique.** `select jobname, schedule from cron.job where
    jobname='anonymize-rental-applications'` returns exactly one row with schedule
    `35 3 * * *`, and no other job in `cron.job` shares that schedule string.
11. **Grant lockdown.** `authenticated` and `anon` calling
    `anonymize_old_rental_applications()` → denied (`REVOKED_CODES`).
12. **GDPR cascade.** Create a disposable user with a property, unit, link and application.
    Call `anonymize_deleted_user(<that user>)`. Assert zero rows remain in BOTH
    `rental_applications` and `rental_application_links` for that owner. Assert the
    pre-existing cascade behaviour still holds — the user row is redacted and the
    notifications rows are gone — so a `create or replace` that dropped part of the old
    body fails here rather than in production.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `anon` → PostgREST | The single most important boundary in the phase. These tests are the only place it is exercised. |
| owner A → owner B | Two paying customers' applicant PII separated only by an RLS predicate. |
| the test suite → production | These tests write to and mutate live configuration. The suite is itself a risk surface. |
