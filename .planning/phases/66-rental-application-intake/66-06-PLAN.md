<objective>
Apply the four migrations to production, reconcile the repo filenames to the timestamps
production assigns, regenerate `src/types/supabase.ts`, and smoke-test the two things
that cannot be proven from the repo.

Purpose: every plan from wave 4 onward reads generated types or calls these RPCs. Until
this plan runs, none of them can be verified honestly.

**This plan is `autonomous: false`.** Applying a migration to production is irreversible
and there is no local Supabase stack to rehearse against.

## Why this is a separate, blocking plan and not a step in 66-01

`bun run typecheck`, `bun run lint` and `next build` all pass **whether or not these
migrations are ever applied**, because TypeScript reads the generated
`src/types/supabase.ts` file, not the live database. A fully green CI is therefore not
evidence that the schema exists. This project has already shipped that exact
false-positive: three v9.0 migrations sat unapplied in production with every check green
until an audit on 2026-07-17 caught them.

## Why not `supabase db push`

There is no local Supabase stack in this repo, so `db push` targets **production
directly** — and the CLI has a standing auth failure here (`functions deploy` 401s on a
PAT that authenticates fine for `projects list`). The established, working path is
Supabase **MCP** `apply_migration`, which assigns its own timestamp that drifts from the
repo filename, followed by a filename reconcile via `mcp__supabase__list_migrations`.
That reconcile is not bookkeeping — an unreconciled filename means the next developer
cannot tell applied migrations from unapplied ones, which is how the v9.0 incident stayed
invisible.
</objective>
