## Why this phase gets real browser coverage where Phase 65 did not

`/apply/[token]` is **public and unauthenticated**, so Playwright drives it with no auth
fixture, no storage state and no session setup — a real browser, real layout, real CSS
cascade. Phase 65 shipped an inert `truncate` and a flattened `space-y` rung because jsdom
computes no layout and a unit test over source can only prove a class is *present*, not
that it *works*. Every row below is a geometric or ordering assertion, never a class check.
</objective>

<interfaces>
**Seeding a real token without browser auth.** The `public` Playwright project runs with
`storageState: { cookies: [], origins: [] }`. That constrains the *browser*, not the test
process. The spec creates a Supabase JS client with the publishable key, signs in as the
synthetic owner via `auth-helpers.ts`'s credentials, calls
`create_application_link(unitId)` (granted to `authenticated`, plan 66-04), and drives the
browser to `/apply/<raw_token>` with no cookies at all. Revoke the link in `afterAll`.

If the owner has no unit, **skip cleanly** rather than creating one — the same
probe-and-skip discipline `lease-signing-tokens.rls.test.ts` uses for its deploy gate.

**The submit path cannot be exercised end to end from localhost, and the spec must not
pretend otherwise.** The deployed Edge Function's CORS check is an exact string comparison
against `NEXT_PUBLIC_APP_URL` (`https://tenantflow.app`), and the E2E browser origin is
`http://localhost:3050`, so a real browser POST is refused before it reaches the function.
Therefore:
- **Context** is fetched server-side by the RSC — no CORS involved — so the form renders
  against a genuinely valid token. Do NOT stub it.
- **Submit** responses are stubbed with `page.route("**/functions/v1/apply-token", ...)`
  for E-15 and E-16 only. Both are assertions about **client state after a response**, which
  is exactly what a stub can establish honestly.
- The **server** behaviours — honeypot writes zero rows, caps hold, idempotency — are
  proven in plan 66-10 by calling the deployed function from Node, where CORS does not
  apply. Say all of this in the spec's header comment so the split is legible and nobody
  later "upgrades" the stub into a fake proof.
</interfaces>

  comment saying why, because it is the natural choice and it silently passes for the wrong
  reason or fails for the wrong reason.
- **E-7 (APPLY-02, non-optional).** Focus the attestation checkbox, press `Tab`, and assert
  the focused element is the submit button and its id is not `apply-company-website`. Tab
  order is the property; a bot that tabs through the form must not reach the trap, and a
  real user must never land in it.
- **E-8 (APPLY-02, non-optional).** Assert zero matches for

- **E-9 (APPLY-01, non-optional).** `<meta name="robots" content="noindex, nofollow">` is

- **E-10 (APPLY-01, non-optional).** `/apply/<garbage>` returns **HTTP 200** (assert the

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the shipped DOM → the applicant | Whatever fields exist in the rendered page are what an applicant can be induced to type. This spec is the last check on that set. |
| the test harness → the truth | A stubbed response can only prove client behaviour. Treating it as proof of server behaviour is itself a security failure. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-66-11 | Information Disclosure | a forbidden field reaching the shipped page | mitigate | E-8 runs the full selector against the fully rendered DOM, catching a field introduced by any component in the tree regardless of which plan added it. |
| T-66-08 | Tampering | honeypot visible, focusable or in the tab order | mitigate | E-6 (geometry, `not.toBeInViewport()` plus `rect.right < 0`) and E-7 (tab order), replacing `66-RESEARCH.md`'s incorrect `toBeHidden()` prescription. |
| T-66-42 | Repudiation | applicant submitting without the APPLY-06 disclaimer in view | mitigate | E-1 at both viewports, comparing real bounding boxes. |
| T-66-02 | Information Disclosure | token-state enumeration | mitigate | E-10 asserts HTTP 200 **and** byte-identical rendered text between the garbage and expired cases. Any per-state wording difference fails. |
| T-66-10 | Information Disclosure | capability URL indexed | mitigate | E-9 reads the meta tag from the rendered head, not the route module — the deployed head is what a crawler sees. |
| T-66-55 | Tampering | a stub masquerading as proof of server behaviour | mitigate | Stubbing is confined to E-15 and E-16, both client-state assertions, and the header comment records that the server-side honeypot, cap and idempotency proofs live in plan 66-10 where Node's lack of CORS makes a real call possible. |
