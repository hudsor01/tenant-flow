`/applications/<id>` — a sheet would have nowhere to land.

**Action bar state machine (§B-6) — three inputs, three outcomes:**

| `status` | `converted_tenant_id` | Primary control | Secondary |
|---|---|---|---|
| `new` \| `reviewing` | null | **Approve and open tenant form** (filled primary) | `Mark reviewing` (outline, only when `new`) · `Decline` (outline) |
| `approved` | null | **Open tenant form** (filled primary) | `Decline` (outline) |
| any | set | **View tenant** (outline) | — |

**Helper line beneath the primary control**, always rendered, `text-xs text-muted-foreground mb-0`:
> Marks this application approved and opens the tenant form with these details filled in. The tenant record is not created until you submit that form.

For the converted case: "Converted to tenant {Name} on {date}." And when the tenant was
later deleted (`converted_tenant_id` nulled by `on delete set null`): "The tenant record
created from this application no longer exists."

same headings** the applicant saw: About you, Where you live now, Income, Household,
References. An owner reading the record in the applicant's own order can spot a

Each card body is the `<dl>` from `<interfaces>` — single column below 640px, two columns at
`sm`. Every `<dd>` carries `mb-0` with a comment naming the parent box (§D-3): it is the
last child of a `flex flex-col gap-1` wrapper.

**Optional fields the applicant left blank render "Not provided" in
`text-muted-foreground` — they are NOT hidden.** The owner needs to see that a field was
offered and skipped; hiding it makes an unanswered optional question indistinguishable from
one that was never asked, which matters on a fair-housing-regulated form.

Do not add a card, field or badge for anything the form does not collect. In particular do
not surface `submitted_ip` or `submitted_user_agent` — they are abuse-investigation data,
not applicant information, and rendering them invites an owner to treat them as signal
about a person.

**Decline dialog** — a `Dialog`, not a `ConfirmDialog`, because a reason must be captured:
- Title "Decline this application".
- Body "Choose a reason. This is stored with the application and is kept after applicant
  details are removed, so you can show why a decision was made."
- A **required** `Select` with `aria-label="Reason"` over `DISPOSITION_REASONS` — the closed
  seven-item vocabulary from plan 66-02, which matches the DB CHECK constraint exactly. It
  is a fixed list precisely so it can never become free-text PII, which is what lets it
  survive anonymization (D-11d).
- Confirm `Button` **default variant, not destructive**, labelled "Decline application".
  Cancel `Button variant="outline"`.
- Submitting calls `setApplicationStatusMutationOptions` with `p_status: "rejected"` and the
  chosen `p_disposition_reason`. The RPC rejects a null reason (plan 66-04), so the UI must
  keep the confirm disabled until one is chosen rather than surfacing a server error.

**No destructive styling and no second confirmation.** Decline is reversible (the status can
be changed back), it sends the applicant nothing (D-10), and it deletes nothing. Red styling
on a fair-housing-regulated decision surface reads as a judgment about the person.

The trigger label is the short `Decline`; the committing button is the explicit `Decline
application`. Comment that the asymmetry is deliberate (§B-8).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| applicant free text → owner's authenticated dashboard | The detail page renders every applicant-supplied string. This is the widest stored-XSS sink in the phase. |
| application id → URL / logs / Referer | Anything placed in the conversion query string is copied into Vercel access logs, browser history and outbound `Referer` headers. |
| owner decision → the durable record | What the owner records here is the evidence a fair-housing claim would be answered with. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-66-09 | Tampering | stored XSS from applicant free text into an authenticated session | mitigate | Every value renders as a React child. **No `dangerouslySetInnerHTML` anywhere in this phase.** Free-text fields (`reason_for_moving`, `pet_details`, `vehicle_details`, `owner_notes`) are the highest-risk and are rendered as plain `<dd>` children. Values were length-capped at the validator (plan 66-02). |
| T-66-11 | Information Disclosure | applicant PII in a query string | mitigate | The conversion href carries the application id only, asserted by an anchored regex in the unit test and again by E-21 in a real browser. The tempting shortcut — appending `&email=` to make prefill "just work" — writes PII into three durable logs outside the retention sweep. |
| T-66-48 | Information Disclosure | abuse-investigation data presented as applicant information | mitigate | `submitted_ip` and `submitted_user_agent` are never rendered; gated by grep. |
| T-66-16 | Repudiation | a decision with no recorded reason | mitigate | The decline dialog requires a closed-vocabulary reason, the confirm stays disabled without one, and the RPC rejects a null reason server-side (plan 66-04). The reason survives anonymization (D-11d). |
| T-66-49 | Repudiation | the owner destroying their own fair-housing evidence unknowingly | mitigate | Delete is the only destructive action, lives in an overflow menu, and its confirm names the two-year retention purpose explicitly. |
| T-66-50 | Information Disclosure | `[deleted]` sentinels presented as applicant data | mitigate | The anonymized branch suppresses the PII cards entirely and renders an explanatory banner; a test asserts `[deleted]` appears nowhere. |
| T-66-14 | Elevation of Privilege | mutating another owner's application | transfer | Every mutation is an owner-gated RPC (plan 66-04); the client never asserts ownership itself. |
| T-66-SC | Tampering | package installs | mitigate | Zero packages. |
</threat_model>
