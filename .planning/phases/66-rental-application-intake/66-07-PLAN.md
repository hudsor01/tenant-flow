Purpose: APPLY-02 — an Edge-Function-mediated insert with `verify_jwt=false`, per-IP rate

Output: the function, its `config.toml` block, and a Node-side contract guard.

## Why an Edge Function and not an anon RLS INSERT policy — the substance, not the rule

The requirement mandates it, but the mandate is downstream of three concrete properties an
anon INSERT policy structurally cannot have:

1. **The caps cannot be enforced.** An RLS policy is a row-level predicate evaluated
   against the row being written. It cannot take a `FOR UPDATE` lock on the link row, read
   `submission_count`, decide, and increment — that is a transaction, not a predicate. So
   with an anon policy the fail-closed bound (F-6) simply does not exist.
2. **There is nowhere to put the honeypot or the rate limit.** Both are request-level
   concerns. PostgREST hands RLS a row, not a request; there is no `req` to read an IP
   from and no place to return a silent 200.
3. **The write surface becomes directly discoverable.** An anon INSERT policy makes
   `POST /rest/v1/rental_applications` a public API. An attacker skips the form entirely
   and every check with it. With the Edge Function the service-role key never leaves the
   function, `anon` holds zero table privileges (plan 66-01), and `submit_rental_application`
   is granted to `service_role` alone (plan 66-04) — so there is no reachable path at all.

Write that reasoning into the function's header comment. A future reader looking at 200
lines of orchestration will otherwise wonder why an INSERT policy would not be simpler.
</objective>

**Request envelope**
```
POST { action: "context", token: string }
POST { action: "submit",  token: string, submission_id: string,
       form_loaded_at: number, company_website?: string,
       application: Record<string, unknown> }
```

**Response contract — every genuine outcome is HTTP 200.**
```
context → { valid: true,  reason: null, listing: { property_label, unit_label,
                                                   rent_amount, owner_display_name } }
        | { valid: false, reason: "invalid_token" | "expired_token" | "revoked_token" }
submit  → { success: true }                       // includes honeypot / timing drops
        | { success: false, reason: "link_capped" | "rate_capped" | "invalid_payload"
                                  | "invalid_token" | "expired_token" | "revoked_token" }
```
Only a transport or server fault produces a non-200 (500 via `errorResponse`), plus the
limiter's own 429.
