# Phase 56 — UI Design Contract

> Visual and interaction contract for the Reporting Hub phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker, then **revised post-approval twice** — see §"Post-approval revision" immediately below.
>
> **This phase is INFORMATION ARCHITECTURE, not new visual language.** The duplicated financial-statement surfaces — `/financials/*` and the chart-bearing `/reports/*` index — collapse into one `/reports` hub. **No analytics route moves.** Reports is *financial statements and exports, with zero charts*; Analytics is *every chart, operational and financial*. Two peer product surfaces, two nav entries, two URL trees. No new report types, no new charts, no new npm deps, no new registry blocks. Every token below is the real value read from `src/app/globals.css` (`@theme`). Every surface composes primitives already vendored in `src/components/ui/`.
>
> **The design job is composition and hierarchy.** Two problems are solved in §"Design Problem 1" and §"Design Problem 3" below. **Design Problem 2 (the `/documents` landing) has MOVED to Phase 65** and is preserved verbatim in §"MOVED TO PHASE 65" at the end of this document. Everything else is inherited: the existing tile pattern (`financials-quick-links.tsx` `QuickLinkCard`), the existing card grid (`report-card-grid.tsx`), the shipped metric-tile shape (`ledger-balance-strip.tsx`), the existing paywall rail (`PaywallError` → sonner toast).
>
> **Load-bearing inherited rule (D-18):** lease-derived figures are labelled **Scheduled**, ledger figures are **Collected**, and nothing sums them. See §"Inherited Vocabulary Guard" — it now governs the hub index directly, because the index renders revenue figures (D-30).
>
> **ZERO-CHARTS INVARIANT (D-34), grep-checkable and binding on every section below:** after this phase, no `recharts` import, no `ChartContainer` and no `ResponsiveContainer` may appear anywhere under `src/app/(owner)/reports/**`.

## Design Problem 1 — `/reports` hub index IA (D-01, D-03, D-30, D-31)

**The page is a summary strip over a directory of 7 destinations. It must earn being a page — not read as a link dump, and not as a second dashboard.**

> **REVISED Round 2: 8 tiles → 7, three groups → two, and the index is no longer data-free.**
> Round 1 had already cut five `/reports/analytics/*` sub-tiles. Round 2 cuts the sixth analytics entry — the Analytics group and its single tile — because nothing analytics-shaped survives inside `/reports` (D-29/D-34). Round 2 also **supersedes D-04**: on 2026-07-30 the user chose *"Summary strip + statement list"* over *"Statement list only (pure navigation index)"*, so the index carries live figures (D-30).

### Primary visual anchor

**The summary strip is the primary visual anchor below the header.** It is the first block a user's eye lands on in the content area, it carries the only large-format numerals on the surface (`text-xl`), and it is the single element that makes `/reports` a page rather than a menu (D-30). The statement list, though larger in total area, is deliberately uniform and recessive: five equal cards, no size or color variation between them, so none competes with the strip. Exports sit last. **If an executor has to choose what dominates, it is the strip.**

### Composition

`/reports/page.tsx` is a **Server Component shell** with **one** `'use client'` island — the summary strip, which is the only element on the page with a data dependency. Contract, checkable by grep: **the page file itself has no `"use client"`; the tile grid has no hooks, no `useQuery`, no `supabase` import; and nothing anywhere under `src/app/(owner)/reports/**` imports `recharts`, `ChartContainer` or `ResponsiveContainer`** (D-34).

### Summary strip contract (D-30) — three tiles, one payload

Metric-tile shape reused verbatim from the shipped ledger pattern (`src/components/ledger/ledger-balance-strip.tsx`): `Card` + `CardContent p-4`, a `text-sm text-muted-foreground` label row with a 16px lucide icon, and a `text-xl font-semibold tabular-nums leading-snug` value.

| Tile | Value | Text color |
|------|-------|-----------|
| Scheduled | lease-derived scheduled rent for the current period | default foreground |
| Collected | ledger receipts for the current period | `text-success-text` when `> 0`, else default |
| Outstanding | `scheduled − collected` **from the same payload** | `text-warning-text` when `> 0.005`, else default |

**Single-source rule (D-18/D-30, load-bearing).** All three figures come from **one** collection-rate payload. Outstanding is `scheduled − collected` **from that same payload** — it MUST NOT come from `get_financial_overview.accounts_receivable`, which is a different, lease-derived notion of outstanding. Sourcing it there would make "Outstanding" mean two different things on two surfaces, which is exactly what D-18 forbids. Scheduled and Collected are **never summed**; subtraction within one period is the defined complement of the collection rate and is permitted.

**Money boundary (Phase 55 D-00).** Ledger values are `numeric(10,2)` **dollars**. Pass straight to `formatCurrency`. Any `* 100`, `/ 100` or `formatCents` is a bug — this caused a real 100× overstatement in v8.0.

**Strip states.** Loading: 3 `Skeleton` tiles at the strip's own height, never a full-page spinner and never blocking the statement list below. Empty: an owner with no ledger data sees **Collected = $0 honestly**, never a fabricated figure and never a hidden tile (Phase 55 D-08). Error: the strip degrades to inline muted copy; **it must never take down the statement list**, which has no data dependency and must always render.

**`ledger-balance-strip.tsx` itself is NOT modified by this phase** — it is Phase 55 shipped code, and the two strips never render on the same route (ledger strip: lease-detail ledger tab; summary strip: `/reports`).

### Tile anatomy (uniform across all 7 — uniformity is the design)

Adapt `QuickLinkCard` from `financials-quick-links.tsx` with the `value`/`trend` props **removed** (the tiles carry no data; only the strip does). Four fixed slots:

1. **Icon medallion** — `size-10 rounded-lg bg-muted flex items-center justify-center`, lucide icon `size-5 text-foreground`, `aria-hidden="true"`. *Neutral, not `bg-primary/10`* — the accent budget is spent elsewhere (see §Color).
2. **Title** — 16px / 600 / `text-foreground`. Report names stay Title Case (they are document names).
3. **Description** — 14px / 400 / `text-muted-foreground`, one line of copy that answers "which one do I want?", never "what is this".
4. **Tier badge** (conditional) — top-right, `Badge variant="outline"` + `Sparkles` `size-3` + label `Growth`. Only on the two entries whose CTA actually hits a gated `reportType` (see §Tier Gate Contract).

Plus the inherited hover affordance: `ArrowRight size-4` top-right, `opacity-0 group-hover:opacity-100`, `aria-hidden="true"`. When a tier badge is present it occupies the top-right and the `ArrowRight` is omitted from that tile (never stack both).

Whole tile is one `<Link>` — `group bg-card border border-border rounded-lg p-5 hover:bg-muted/50 hover:border-primary/30 transition-colors`. **One link per tile, zero nested interactive elements.**

### The D-20 Accounts Receivable figure — landing surface is an OPEN QUESTION

D-20 ports Accounts Receivable rather than dropping it — it is the one figure that disappears when `/financials` is deleted (`financials-summary-stats.tsx:117-132`). **Round 1 pinned it to `/reports/analytics`; Round 2 deletes that route, so it has no assigned home.** This contract does **not** invent one. Constraints any answer must satisfy:

- **It must NOT be folded into the strip's Outstanding tile.** A/R is `get_financial_overview` lease-derived; Outstanding is `scheduled − collected` from the collection-rate payload. Two derivations under one label is the D-18 failure in its purest form.
- If it lands on the strip it must be a **fourth tile with its own derivation-accurate label**, which changes the strip from `sm:grid-cols-3` to `sm:grid-cols-2 lg:grid-cols-4`.
- If it lands on a statement route, `/reports/balance-sheet` is where receivables belong in accounting terms.

See CONTEXT OQ-1. A planner may propose; none may treat this as decided.

### States

The **statement and export tiles** have no empty, loading or error state — they render static markup with zero data dependencies. Any skeleton, spinner, `Empty` compound or error boundary around the *tile grid* is a blocking defect.

The **summary strip** is the one place states exist, and they are specified above. The strip's failure must never remove the tiles: an error boundary that takes down the directory is a blocking defect, because the directory is the page's fallback purpose.

No entrance animation on the tile grid. `BlurFade` (used on the legacy `/financials` index) may wrap the header only if the planner keeps the existing pattern; it is **not** applied to the tiles — animating a static directory adds perceived latency to the part of the page whose only job is to get out of the way.

## Typography

Font family `--font-sans` throughout.

> **RESTATED Round 2 (R2-9) — honest counts.** The Round-1 text claimed a flat "exactly two weights, exactly four sizes." That was true only because the index carried no metric values. D-30 adds a summary strip, and the strip reuses the shipped ledger metric-value treatment, which is a fifth size. The contract is therefore **4 base sizes + 1 bounded metric-value exception** (`text-xl`, reused from `ledger-balance-strip.tsx`) and **2 base weights + 1 bounded `<h1>` exception** (700, a single element per route). Both exceptions are named, scoped, and justified below. Neither is a free-floating override, and neither is hidden behind a tidier-sounding count.

| Role | Size | Weight | Line height | Applied to |
|------|------|--------|-------------|-----------|
| Page title | `typography-h1` (24px, `--text-title-1` where fluid) | **700 — weight exception, see below** | 1.2 (`--leading-tight`) | `<h1>` on `/reports` — matches the existing `/reports/year-end` and `/reports` headers. **`[65]`** `<h1>` on `/documents` |
| Section / tile title | 16px (`text-base`) | 600 | 1.35 (`--leading-snug`) | Group `<h2>`; every tile title. **`[65]`** band `<h2>`; the vault panel title |
| Body / description | 14px (`text-sm`) | 400 | 1.5 (`--leading-normal`) | Page subtitle; group one-liners; every tile description; strip labels; button labels. **`[65]`** recent-row title |
| Metadata | 12px (`text-xs`) | 400 | 1.5 (`--leading-normal`) | Tier-badge label. **`[65]`** `Recently added` label; recent-row meta line |
| **Metric value** | **20px FIXED (`text-xl`) — size exception, see below** | 600 | **1.35 (`--leading-snug`) — must be written explicitly** | The three summary-strip figures on `/reports` (D-30) |

**Base sizes (4):** page title, `text-base`, `text-sm`, `text-xs`. **Base weights (2):** 400 regular + 600 semibold.

**Size exception — `text-xl` metric values.** Summary-strip figures use `text-xl font-semibold tabular-nums leading-snug`. This is a verbatim reuse of the shipped ledger pattern (`src/components/ledger/ledger-balance-strip.tsx:52` — `"text-xl font-semibold tabular-nums"`), which Phase 55 established as the house metric-value treatment. It is permitted on **currency and percentage figures inside metric tiles only** — nowhere else on this surface. Folding it onto the fluid section-title role was considered and rejected: a `clamp()`-based title size shrinks the figure below 20px at narrow viewports while the shipped ledger strip holds at 20px, making the two strips diverge for the same data. **Consistency with shipped code beats an artificially low size count.**

**Line-height is mandatory on this role.** `globals.css` defines `--text-xl` with **no paired `--text-xl--line-height`**, so a bare `text-xl` leaves the line box to an implicit fallback rather than a declared token. Write `leading-snug` (1.35) explicitly on every metric value. 1.35 is the same line-height this system already gives its other ≤20px title-weight text, so the strip and the tile titles sit on a consistent vertical rhythm.

**Weight exception — `typography-h1` at 700.** `typography-h1` carries weight 700 as a global token. It is permitted on **exactly one element per route — the `<h1>`** — and nowhere else. Justification: `typography-h1` is already the house page-title utility on `/financials`, `/analytics/financial`, and every other owner surface; forcing a phase-local override would make the moved hub visually inconsistent with its siblings. **Free-floating `font-bold` on any non-`<h1>` element fails this contract.**

**Honest pixel-count disclosure.** Where the section-title role resolves through a fluid `clamp()` (16 → 20) and `text-xl` is fixed at 20, a single `/reports` viewport can render up to **five simultaneously-distinct pixel sizes**: 12 (badge), 14 (labels/descriptions), 16–20 (section and tile titles), 20 (metric values), 24–30 (page title). At the top of the title clamp (viewport ≥ ~1000px) titles and metric values converge to 20px and the count drops to four. **This is stated rather than papered over: the contract is 4 base sizes plus one bounded exception, not "4 sizes" flat.**

**Metric-value invariant:** `tabular-nums` is MANDATORY on every currency and percentage figure so columns align.

**Two-weight discipline — the required overrides.** The adapted patterns default to weight 500 (`font-medium`), which would introduce a third *base* weight:

1. `QuickLinkCard`'s tile title (`financials-quick-links.tsx:43`) is `font-medium` → use **`font-semibold`**.
2. `ReportCardGrid`'s group heading (`report-card-grid.tsx:32`) is `font-medium` → use **`font-semibold`**.
3. **`[65]`** `ItemTitle`'s primitive default is `font-medium` → override to **`font-normal`** on recent-document rows (they are metadata, not headings).

Scope note: `main-nav.tsx` keeps its existing `font-medium` treatment. Nav chrome is pre-existing styling this phase does not restyle — and after the revisions only its `href`s and item set change. **Its active-state logic is not touched** (see Design Problem 3).

**No hierarchy is carried by type size beyond these five roles.** On the hub index, group hierarchy comes from the section headings and their one-liners — every tile title is the same size and weight, because uniformity is the design. The strip's dominance comes from the metric-value role, its position directly under the header, and the tiles' deliberate uniformity — not from a sixth size. **`[65]`** The vault panel's primacy comes from full width, the `size-12` primary-tinted medallion, the page's only filled primary button, and the content it contains — deliberately **not** from an extra font size.

### Design Problem 2 — `/documents` landing composition (D-14..D-17)

**Locked and non-negotiable:** vault entry + lease-template entry + **four separate** printable template cards + a recent-documents list. Six tiles plus a list. The two real problems are (a) six tiles skew weight toward templates when the vault is the primary destination, and (b) the recent list overlaps `/documents/vault` and the two must not visibly disagree.

**Both are solved by one move: the recent-documents list lives INSIDE the vault panel, and the vault panel is a full-width primary band that the templates cannot compete with.**

#### Three-band descending-weight ladder

```
BAND 1 — Vault (full width, bg-card, p-6, contains the recent list)

  │   FolderArchive text-primary                                     │

  └────────┘ └────────┘ └────────┘ └────────┘
```

**Why this fixes balance (a):** the vault occupies full width, carries a `size-12` primary-tinted medallion, is the page's only filled primary `Button`, and contains live content — roughly half the page's vertical real estate. Below it, six tiles read as **1 + 4** across two labelled bands with progressively smaller medallions (`size-10` → `size-8`) and padding (`p-5` → `p-4`) and neutral `bg-muted` medallions. Tile count is untouched (D-16 satisfied: four separate cards); the hierarchy is carried by size, width, color budget, and content — not by deleting anything.

**Why this fixes overlap (b) — two independent guarantees:**

1. **Semantic:** nesting the list inside the vault panel, under a `Separator`, below the "Open the vault" CTA, makes it read unambiguously as *a preview of what is in the vault* rather than a second, competing document surface. It is subordinate by position, never a sibling band.
2. **Structural — they cannot disagree, by construction:** the list calls `documentSearchQueries.list({ page: 0 })` from `#hooks/api/query-keys/document-search-keys` with **no filters** and slices the result to the first 5 client-side. That is the exact factory the vault client calls (`src/components/documents/documents-vault.client.tsx:230-238`) → the same `search_documents` RPC → the same `mapDocumentRow` boundary mapper → the same TanStack Query cache entry. The RPC's unfiltered ordering is `d.created_at desc` (verified: `20260426043911_v25_phase_63_search_documents_filter_extension.sql:110`), so "recent" is exactly the vault's own first rows.

**Scope of the "same cache entry" claim (checker-verified):** it holds for the vault's *default, unfiltered landing state* — `queryParam=""`, `entityType=undefined`, `categories=[]`, `from`/`to=""`, `page=0` — which normalizes to the identical query key as `documentSearchQueries.list({ page: 0 })`. Once the owner types a search or applies a filter the vault moves to a different key, and the landing's list legitimately keeps showing unfiltered recents. That is correct behaviour, not drift: the two only ever share a cache entry when they are asking the same question. **Building a second query, a second mapper, or a direct `.from('documents')` select is a blocking violation of this contract.**
