# 66.1 PLAN CHECK — verdict: BLOCK

Goal-backward review of `66.1-01` .. `66.1-05` against: *limits that actually enforce, in the same
failure domain as the writes they guard, failing closed, observable when broken, keyed on an
identity an attacker cannot forge.*

**Verdict: BLOCK.** 4 blockers, 5 warnings, 1 info. Every blocker is in a **gate**, not in the
design: four automated verifies either cannot fail, or cannot pass while the plan's own acceptance
criteria are met. The mechanisms themselves are sound and the requirement coverage is complete.

## What passes (verified, not assumed)

- **Requirement coverage.** RATE-01/02/03/04 each appear in the `requirements` frontmatter of at
  least one plan and each has covering tasks. All 14 deferrals 03 and 04 hand forward are
  enumerated in 05 `<what_03_and_04_deferred_to_this_plan>` and each maps to a task that performs
  it. No orphaned deferral.

  boundary test on *two* assertions (`allowed === false` **and** an exact head-count of 0 rows at

  `do update` unconditional, so 01 Task 2's main run admits 2,560 of 2,560 against `admitted ===
  100`. Both are genuinely falsifiable.
- **Concurrency is non-vacuous.** 64 `Promise.all` workers, `peakInFlight >= 32`, and a client-side
  check-then-act control asserted `> LIMIT` *strictly* with a failure message stating that an equal
  result makes every exact-100 assertion vacuous. The plan states the honest limit (request-level
  interleaving through PostgREST; the pgbench statement-level proof is in RESEARCH and is not
  re-run).
- **Fail-closed is executed, not grepped.** 03 splits the taxonomy into a zero-import,
  zero-runtime-global leaf specifically so Vitest can run `decideRateLimit({kind:"thrown"}) ->
  denied, db_unreachable` for real, plus a closure test that exactly one input shape admits. The
  glue is source-pinned by balanced-brace slicing (no `catch` contains `return null`), and 05 Task
  6 proves it live by revoking EXECUTE and requiring 429.
- **The unset-secret bypass is handled correctly and probed live.** Guarded on both sides
  independently (RSC refuses an empty-after-trim secret; `decideForwardedClientIp` checks
  `configuredSecret` emptiness *before any comparison runs*), verified as shipped by index
  comparison + an executed matrix row, and proven in production in the deploy-before-secret window
  with **both halves** — zero rows for the forged address AND the real address's counter moving by
  exactly 3. The non-vacuity half is what makes this real.
- **Sentry acceptance is client-BOUNDNESS.** 03's Deno test asserts `Sentry.getClient()` is defined
  and its `dsn` option matches, explicitly rejecting "captureException was called" because it
  returns an event id either way. Confirmed against the repo: `Sentry.init` appears exactly once,
  `stripe-webhooks/index.ts:32`, and `_shared/errors.ts` calls `captureException` unbound.
- **The `extra` -> `tags` correction is right.** Sentry issue alerts cannot filter on `extra`; 05
  Task 1(d) adds an optional `tags` argument and passes `{event, error_class}`, and Task 6(d)
  refuses to mark RATE-04 met until the rule reaches a human. T-66.1-35 states honestly that no CI
  check can verify the rule exists.
- **The RSC header gate is a hard gate.** 05 Task 8(b) has three named outcomes, a real remedy
  (record UNMET + the instant kill switch of unsetting the Supabase secret, no deploy needed) and
  forbids improvising a fix. Task 8(e)'s second-client-on-a-different-network check is the only
  assertion that separates "per-client limit" from "product-wide cap that denied you first", and it
  is present.
- **Version bump is not trusted as delivery proof.** 05 Task 5(c) byte-compares the platform's copy
  of `_shared/rate-limit.ts` and `_shared/rate-limit-decision.ts` against disk.
- **Factual claims spot-checked and correct:** 11 `rateLimit()` call sites (sign-lease-token 4,
  lease-signature 3 at 203/385/590, apply-token 2, send-contact-email 1, newsletter-subscribe 1);
  deploy script carries all five slugs; migration house style is `--` line comments so the
  `sed 's/--.*//'` strip works; nothing in `package.json` or `.github/workflows/` runs `deno test`.

## BLOCKERS

### B1 — Every `bun run test:unit -- --run <file>` in 66.1-04 and 66.1-05 crashes before a test runs

**Plans/tasks:** 04 Task 1 verify; 04 Task 2 verify; 04 Task 3 verify (x3); 04 `<verification>`
(x4); 05 Task 1 verify (x2); 05 `<verification>` (x4). ~15 sites.

`test:unit` is `vitest --run --project unit`, so `-- --run <file>` passes `--run` twice. Measured on
this machine:

```
$ bun run test:unit -- --run supabase/functions/__tests__/application-guards.test.ts
Error: Expected a single value for option "--run", received [true, true]
error: script "test:unit" exited with code 1
```

**What breaks.** These invocations sit at the head of an `&&` chain, so the whole verify aborts and
*none* of the structural greps behind them is ever evaluated. Every acceptance criterion in the two
plans that carry RATE-03 and go-live is unverified. The cheapest improvisation is to drop the file
argument and run the entire unit suite — which `deferred-items.md` D1 records as intermittently red
on unrelated commits, converting the gate into a coin flip.

This is a transcription slip, not a judgement call: 66.1-02's own `read_first` documents the correct
form ("`test:integration` already contains `--run`, so the invocation is ... a bare positional
filter and no second `--run` flag"), and 66.1-03 uses it correctly throughout.

**Fix:** delete `--run ` from every `bun run test:unit --` invocation in 04 and 05. Verified working
form: `bun run test:unit -- supabase/functions/__tests__/application-guards.test.ts` -> 89 passed.

### B2 — The pure-ASCII gate in 66.1-01 and 66.1-02 can never fail

**Plans/tasks:** 01 Task 1 `<verify>`; 02 Task 1 `<verify>`.

Both use `LC_ALL=C grep -qP "[^\x00-\x7F]" "$F" && { echo "FAIL non-ascii"; exit 1; }` inside
`bash -c`. Inside `bash -c` the interactive `grep`->ugrep shim does not exist, and BSD
`/usr/bin/grep` has no `-P`. Measured:

```
$ bash -c 'set -e; LC_ALL=C grep -qP "[^\x00-\x7F]" /tmp/x.txt && { echo FAIL; exit 1; }; echo reached-next-step'
grep: invalid option -- P
reached-next-step        <- guard skipped, exit 0
```

grep exits 2, the `&&` short-circuits, and `set -e` does not fire because the failing command is not
the last in an AND-list. The guard is a permanent pass.

**What breaks.** 01's acceptance criterion "Pure ASCII" and 02's "the file is still pure ASCII
(re-check; this is the last moment before the bytes go over the wire)" are both unverifiable. ASCII
is load-bearing here and the plans say so: it is the stated reason the phase can tolerate the
model-mediated apply hop (`edge-deploy-mcp-fidelity`), and 02 explicitly says "66.1-01 made the file
pure ASCII specifically to shrink this risk; do not spend the margin it bought." The margin is
already spent — the gate does not exist. The risk is not hypothetical: 01's migration header is
several hundred lines of prose where em-dashes and curly quotes are the default model output.

This is the eighth green-but-proves-nothing mechanism the phase was told to look for, and it guards
the property the apply path depends on.

**Fix:** replace both with a portable check that fails on non-ASCII bytes:
`test -z "$(LC_ALL=C tr -d '\000-\177' < "$F")" || { echo "FAIL non-ascii"; exit 1; }`

### B3 — 66.1-03 Task 2's verify cannot pass while its own acceptance criterion is met

**Plan/task:** 03 Task 2, `<verify>` vs `<action>(c)` and the matching acceptance criterion.

The verify asserts `test "$(grep -c "timeout" "$R")" -eq 0` over the whole of `rate-limit.ts`. The
action requires the file to carry a comment naming "the migration's `lock_timeout = '250ms'` as what
bounds the only unbounded case", and the acceptance criterion restates both halves in one sentence:
"Zero occurrences of `timeout` ... **with a comment naming the migration's `lock_timeout =
'250ms'`**". `lock_timeout` contains `timeout`. The two cannot both hold.

**What breaks.** The executor must break one. The cheapest resolution is deleting the comment — and
that comment is the sole guard-rail against D-07 being reversed. The plan itself says so: "Say this
explicitly, or someone re-adds the timeout as a 'safety net'." Task 3's version of the same check is
already correct (it runs against comment-stripped source); Task 2's is not.

**Fix:** in 03 Task 2's verify, count against comment-stripped source, matching Task 3:
`test "$(sed 's://.*::' "$R" | grep -c timeout)" -eq 0`

### B4 — 66.1-01's GUARD 2 grep counts the header comment the same task requires

**Plan/task:** 01 Task 1, `<verify>` vs `<action>` header item 2.

`grep -cE "where c\.request_count \+ v_prev_weighted < p_max_requests"` must return exactly 1. The
action requires the header to "Reproduce the reasoning in
`<the_defect_this_plan_exists_to_prevent>` above", and that section lists both guards verbatim,
including GUARD 2 as `` `where c.request_count + v_prev_weighted < p_max_requests` ``. Faithful
compliance yields 2 and the verify prints `FAIL guard2=2`.

GUARD 1's grep is immune only by accident: it is line-anchored (`^[[:space:]]*where ...$`), so a
`--`-prefixed comment line cannot match. GUARD 2's is unanchored. The verify already builds a
comment-stripped copy (`STRIP=$(sed "s/--.*//" "$F")`) for its `_archive` / `create type` / policy
counts and simply does not use it for the guards.

**What breaks.** A deterministic failure on the phase's single most important structural assertion.
The likely improvisation is to strip the reasoning out of the header — the reasoning 01 calls "THE
TWO GUARDS ARE THE DESIGN" and deliberately puts in the file a future editor will actually open.

**Fix:** count both guards against `$STRIP` (move the `STRIP=` assignment above the guard counts and
use `printf %s "$STRIP" | grep -cE ...`), or line-anchor GUARD 2 the way GUARD 1 already is.

## WARNINGS

### W1 — Two 66.1-05 production probes order by a column that does not exist

**Plan/tasks:** 05 Task 5(d) and Task 8(b).

Both run `... from public.rate_limit_counters where bucket_key like '...' **order by window_start
desc** limit 5`. The table 66.1-01 creates has exactly `bucket_key`, `window_index`,
`request_count`, `expires_at` (RESEARCH.md lines 137-145). `window_start` does not exist; both
queries fail with `42703 undefined column`.

Task 5(d) is how every later probe learns "the real address"; Task 8(b) is **THE HARD GATE** for
RATE-03. Both fail on a typo, mid-go-live, with a public surface already changed.

**Fix:** `order by window_index desc` in both.

### W2 — `await headers()` placement is unspecified, and the obvious placement is inside a
swallow-everything `catch`

**Plan/task:** 04 Task 1 `<action>`, wiring into `fetchApplyContext`.

`src/app/apply/[token]/apply-context.ts:93-107` already has `try { ...fetch... } catch { return
{ valid: false, reason: "context_error" } }`. The plan says "Do **not** wrap `headers()` in a
try/catch" and gives the right reason ("a swallowed throw would make the mechanism a permanent
silent no-op"), but it never says the call must be placed **before** the existing `try` at line 93.
An executor who puts `const h = await headers()` next to the fetch adds no try/catch and satisfies
every stated criterion — and lands inside a catch that swallows the throw into `context_error`,
producing exactly the permanent silent no-op the plan forbids. No test can catch it: 04 Task 1's own
suite mocks `next/headers`, so it never throws.

**Fix:** add an acceptance criterion and a source assertion in
`src/app/apply/[token]/__tests__/apply-context.test.ts`: the index of `await headers()` inside
`fetchApplyContext` is strictly less than the index of `try {`.

### W3 — Both headline behavioural proofs are one-shot manual runs with no automated runner

Two files, both correctly designed, neither of which will ever run again after the phase:

1. `tests/integration/rls/rate-limit-concurrency.rls.test.ts` — the 64-client RATE-01 proof — gates
   on `SUPABASE_SERVICE_ROLE_KEY ?? SUPABASE_SECRET_KEY` through `describe.skipIf`.
   `.github/workflows/rls-security-tests.yml`'s "Check required secrets" step enumerates six
   secrets (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, four E2E owner
   creds) and neither service-role name is among them. The file will skip silently on every future
   PR. Only 66.1-02 Task 4 ever demands zero skips, and it runs once, by hand.
   That same workflow's own comment says a silently skipping security gate "is the worst possible
   failure mode — it certifies isolation it never checked."
2. `supabase/functions/tests/rate-limit-sentry-test.ts` — the client-BOUNDNESS proof, and the only
   executed evidence that `errors.ts` transmits at all — runs only under `deno test`. Confirmed:
   nothing in `package.json` scripts or `.github/workflows/` invokes `deno test`. 66.1-05 puts
   "adding a Deno CI job" explicitly out of scope. 66.1-05 Task 2(d) runs it once more pre-deploy;
   after that, never.

**What this costs, stated plainly:** after go-live, a regression that restores fail-open, unbinds
the Sentry client, or breaks the two-guard statement is caught by **nothing that runs
automatically**. The durable guards degrade to 66.1-03's source greps — the same evidentiary
standard that let the original outage run for months. The tag-forwarding assertion added in 05 Task
1(d) is also source-only; that `tags` actually reach Sentry is proven by exactly one live
observation in Task 6.

Provisioning the CI secret is out of scope by CONTEXT. **The finding is that no plan states the
consequence.**

**Fix (minimum):** 66.1-05's SUMMARY must record that RATE-01's concurrency proof and RATE-04's
binding proof have no automated runner, name the manual commands, and name who runs them next.
Optionally (cheap, in scope): add the service-role key name to `rls-security`'s required-secrets
list so the skip becomes a loud CI failure rather than a silent pass.

### W4 — 66.1-05 must_haves truth #9 contradicts 66.1-05 Task 1(f)

Truth #9: "No file under `supabase/functions/` contains the identifier `UPSTASH_REDIS_REST` or
claims the limiter fails open."

Task 1(f) requires `expect(SERVE_BODY).not.toContain("UPSTASH_REDIS_REST")` to be **added** to
`supabase/functions/__tests__/apply-token-contract.test.ts`; the artifact block specifies that file
as `contains: "UPSTASH"`; and Task 1's own verify asserts `grep -q "UPSTASH_REDIS_REST" "$T"`
(present). All three are correct; the truth is wrong. A verifier taking it literally and running
`grep -rn UPSTASH_REDIS_REST supabase/functions/` reports FAIL on a correct implementation.

**Fix:** scope truth #9 to `supabase/functions/*/index.ts` and `supabase/functions/_shared/`.

### W5 — 66.1-05 Task 8's automated verify rejects the honest-failure path its own `<done>` allows

The `<verify><automated>` hard-requires `"per_client_key_matches_self":true`. The acceptance
criteria and `<done>` both explicitly allow the alternative completion: "the gate failed, RATE-03 is
recorded UNMET with evidence, the kill switch was applied, and a deferred item names the two
candidate follow-ups." As written, taking that path reports as an executor failure rather than as
the disclosed outcome — which pressures the executor toward improvising a fix, exactly what the task
text forbids.

**Fix:** accept `"per_client_key_matches_self":true` **or** `"rate03_unmet_recorded":true` in
`$SCRATCH/rsc.json`.
