## BLOCKERS

### B1 — Every `bun run test:unit -- --run <file>` in 66.1-04 and 66.1-05 crashes before a test runs

**Plans/tasks:** 04 Task 1 verify; 04 Task 2 verify; 04 Task 3 verify (x3); 04 `<verification>`
(x4); 05 Task 1 verify (x2); 05 `<verification>` (x4). ~15 sites.

`test:unit` is `vitest --run --project unit`, so `-- --run <file>` passes `--run` twice. Measured on
this machine:

```
$ bun run test:unit -- --run supabase/functions/__tests__/application-guards.test.ts
Error: Expected a single value for option "--run", received [true, true]
error: script "test:unit" exited with code 1
```

**What breaks.** These invocations sit at the head of an `&&` chain, so the whole verify aborts and
*none* of the structural greps behind them is ever evaluated. Every acceptance criterion in the two
plans that carry RATE-03 and go-live is unverified. The cheapest improvisation is to drop the file
argument and run the entire unit suite — which `deferred-items.md` D1 records as intermittently red
on unrelated commits, converting the gate into a coin flip.

This is a transcription slip, not a judgement call: 66.1-02's own `read_first` documents the correct
form ("`test:integration` already contains `--run`, so the invocation is ... a bare positional
filter and no second `--run` flag"), and 66.1-03 uses it correctly throughout.

**Fix:** delete `--run ` from every `bun run test:unit --` invocation in 04 and 05. Verified working
form: `bun run test:unit -- supabase/functions/__tests__/application-guards.test.ts` -> 89 passed.

### B2 — The pure-ASCII gate in 66.1-01 and 66.1-02 can never fail

**Plans/tasks:** 01 Task 1 `<verify>`; 02 Task 1 `<verify>`.

Both use `LC_ALL=C grep -qP "[^\x00-\x7F]" "$F" && { echo "FAIL non-ascii"; exit 1; }` inside
`bash -c`. Inside `bash -c` the interactive `grep`->ugrep shim does not exist, and BSD
`/usr/bin/grep` has no `-P`. Measured:

```
$ bash -c 'set -e; LC_ALL=C grep -qP "[^\x00-\x7F]" /tmp/x.txt && { echo FAIL; exit 1; }; echo reached-next-step'
grep: invalid option -- P
reached-next-step        <- guard skipped, exit 0
```

grep exits 2, the `&&` short-circuits, and `set -e` does not fire because the failing command is not
the last in an AND-list. The guard is a permanent pass.

**What breaks.** 01's acceptance criterion "Pure ASCII" and 02's "the file is still pure ASCII
(re-check; this is the last moment before the bytes go over the wire)" are both unverifiable. ASCII
is load-bearing here and the plans say so: it is the stated reason the phase can tolerate the
model-mediated apply hop (`edge-deploy-mcp-fidelity`), and 02 explicitly says "66.1-01 made the file
pure ASCII specifically to shrink this risk; do not spend the margin it bought." The margin is
already spent — the gate does not exist. The risk is not hypothetical: 01's migration header is
several hundred lines of prose where em-dashes and curly quotes are the default model output.

This is the eighth green-but-proves-nothing mechanism the phase was told to look for, and it guards
the property the apply path depends on.

**Fix:** replace both with a portable check that fails on non-ASCII bytes:
`test -z "$(LC_ALL=C tr -d '\000-\177' < "$F")" || { echo "FAIL non-ascii"; exit 1; }`

### B3 — 66.1-03 Task 2's verify cannot pass while its own acceptance criterion is met

**Plan/task:** 03 Task 2, `<verify>` vs `<action>(c)` and the matching acceptance criterion.

The verify asserts `test "$(grep -c "timeout" "$R")" -eq 0` over the whole of `rate-limit.ts`. The
action requires the file to carry a comment naming "the migration's `lock_timeout = '250ms'` as what
bounds the only unbounded case", and the acceptance criterion restates both halves in one sentence:
"Zero occurrences of `timeout` ... **with a comment naming the migration's `lock_timeout =
'250ms'`**". `lock_timeout` contains `timeout`. The two cannot both hold.

**What breaks.** The executor must break one. The cheapest resolution is deleting the comment — and
that comment is the sole guard-rail against D-07 being reversed. The plan itself says so: "Say this
explicitly, or someone re-adds the timeout as a 'safety net'." Task 3's version of the same check is
already correct (it runs against comment-stripped source); Task 2's is not.

**Fix:** in 03 Task 2's verify, count against comment-stripped source, matching Task 3:
`test "$(sed 's://.*::' "$R" | grep -c timeout)" -eq 0`

### B4 — 66.1-01's GUARD 2 grep counts the header comment the same task requires

**Plan/task:** 01 Task 1, `<verify>` vs `<action>` header item 2.

`grep -cE "where c\.request_count \+ v_prev_weighted < p_max_requests"` must return exactly 1. The
action requires the header to "Reproduce the reasoning in
`<the_defect_this_plan_exists_to_prevent>` above", and that section lists both guards verbatim,
including GUARD 2 as `` `where c.request_count + v_prev_weighted < p_max_requests` ``. Faithful
compliance yields 2 and the verify prints `FAIL guard2=2`.

GUARD 1's grep is immune only by accident: it is line-anchored (`^[[:space:]]*where ...$`), so a
`--`-prefixed comment line cannot match. GUARD 2's is unanchored. The verify already builds a
comment-stripped copy (`STRIP=$(sed "s/--.*//" "$F")`) for its `_archive` / `create type` / policy
counts and simply does not use it for the guards.

**What breaks.** A deterministic failure on the phase's single most important structural assertion.
The likely improvisation is to strip the reasoning out of the header — the reasoning 01 calls "THE
TWO GUARDS ARE THE DESIGN" and deliberately puts in the file a future editor will actually open.

**Fix:** count both guards against `$STRIP` (move the `STRIP=` assignment above the guard counts and
use `printf %s "$STRIP" | grep -cE ...`), or line-anchor GUARD 2 the way GUARD 1 already is.

## BLOCKER

### N1 — Plan 01 Task 1's entire `<automated>` verify is a bash syntax error and exits 2 before any check runs

**Plan/task:** 01 Task 1 `<verify><automated>` (line 245).

The payload contains `\&\&` where it needs `&&`:

```
test -n "$(LC_ALL=C tr -d "\000-\177" < "$F")" \&\& { echo "FAIL non-ascii"; exit 1; }
```

Inside `bash -c '...'` the single quotes make `\&\&` literal. Bash then sees `\&` as an escaped
literal `&`, `{` stops being a reserved word, and the parse dies:

```
bash: -c: line 1: syntax error near unexpected token `}'
exit=2
```

A syntax error is a *parse-time* failure, so **nothing on that line executes** — not the ASCII guard,
not the GUARD 1/GUARD 2 counts, not the `_archive` / `create type` / `create policy` / `for all`
counts, not the `fillfactor` / `lock_timeout` / `p_window_ms` / cron-minute checks, not the grant-order
`awk`. The whole task verifies nothing and reports failure.

**This is not a regression — it is a cycle-1 miss.** The `\&\&` predates `c34d42a5c` (`\&` count in
plan 01 is 6 both before and after), and cycle 1 silently normalised it to `&&` when quoting the line.
It is reported now because the B2 and B4 fixes were both placed on this line, so **both of those fixes
are currently inert.** Cycle 1's B2 and B4 remain unproven in plan 01 in practice, despite the source
edits being correct.

There is no escaping convention that rescues this. `66.1-01-PLAN.md` is the **only** file in the whole
of `.planning/phases/` containing `\&`; 36 other plan files use bare `&&` inside `<automated>`,
including 66.1-02 through 66.1-05.

The second `\&\&`, inside the grant-order `awk` program, is broken too — `awk` reports
`syntax error at source line 1 ... r>0 >>> \ <<< &\& g>0` and the clause falls through to
`FAIL grant order`.

**Fix:** one global substitution in `66.1-01-PLAN.md`, `\&\&` -> `&&` (2 sites). Verified: the
corrected payload parses clean (`bash -n` passes, 0 `\&` remain), the ASCII guard then passes on ASCII
and fails on an em-dash, the guard counts return `guard1=1 guard2=1` on correct SQL and fail when a
guard is removed, and the `awk` clause passes with `grant` after `revoke` and fails when reversed.

**Ruling: warning.** Cycle 1 asked whether the obvious placement makes the forwarding a silent no-op.
Traced through the real file, **it cannot.**

`src/app/apply/[token]/apply-context.ts:93-107` is `try { fetch(...) } catch { return { valid: false,

a throw is converted into `context_error`, which is indistinguishable from a genuine edge-function

no new constraint), so the throw path is not expected in production.

**Smallest change:** one clause in 04 Task 1's action — place `const h = await headers()` and the
`trustedClientIpHeaders` call **above** the existing `try {` at :93. The durable guard is cycle 1's
proposed source-order assertion (index of `await headers()` < index of `try {`), which costs one
