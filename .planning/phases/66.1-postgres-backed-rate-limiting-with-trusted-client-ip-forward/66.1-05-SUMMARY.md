## MISTAKE MADE AND CORRECTED

I set `SENTRY_DSN` to an EMPTY STRING in production. The extraction returned zero characters and I
piped it straight into `supabase secrets set` without checking. Removed within a minute
(`secrets unset`, verified back to 50). An empty secret is worse than an absent one because it
reads as configured.

The rewrite that caught it validates the value looks like a DSN BEFORE setting, and it is what
surfaced the real blocker: **Vercel marks 40 of its 72 production variables as Sensitive, so their
values export blank** -- `SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_DSN` among them. The DSN was never
retrievable from Vercel by any means, so the earlier plan to copy it across could not have worked.

Resolved canonically instead: fetched from the Sentry API (`find_dsns`), which is the authoritative
source. Two client keys exist for `tenant-flow`, both routing to project `4510717297033216`; used
the one named `tenant-flow`.

# ADDENDUM 2 -- CLIENT_IP_FORWARD_SECRET provisioned, RATE-03 proven live

The "deliberately not done" item above is now done at the owner's instruction. The reasoning for
deferring it was sequencing, not risk: the RSC that signs the forwarded address is still not on
`main`, so nothing legitimate sends the header yet. Installing the secret early is harmless -- the
edge side simply has nothing to trust until the app deploys.

## Provisioning

Generated with `openssl rand -hex 32` (256 bits), validated for length and hex-ness BEFORE
installing anywhere -- the guard whose absence produced the empty `SENTRY_DSN` earlier in this
plan. Installed to BOTH platforms from a single shell variable in one invocation, which is what
guarantees the two halves match: neither platform allows reading a secret back, so a two-step
copy could not have been verified.

- Supabase function secret `CLIENT_IP_FORWARD_SECRET` -- present, non-empty (52 secrets)
- Vercel Production env `CLIENT_IP_FORWARD_SECRET` -- present, Encrypted
- `NEXT_PUBLIC_CLIENT_IP_FORWARD_SECRET`: **0 occurrences** in Vercel and 0 in source. A
  client-exposed copy would hand every visitor the ability to forge their own rate-limit identity.

Production only, deliberately. Preview and Development are left without it, so preview deployments
fall back to the connection address -- consistent with minimising what those environments hold.

## THE FULL TRUST MATRIX, PROVEN AGAINST THE DEPLOYED FUNCTION

Read from `rate_limit_counters` after each probe, so the evidence is the bucket the limiter
actually keyed on, not the HTTP status.

| scenario | resulting bucket_key | verdict |
|---|---|---|
| valid secret + `x-tf-client-ip: 203.0.113.77` | `contact:203.0.113.77` | **forwarded address HONOURED** |
| valid secret + malformed address (`not-an-ip-at-all;drop table`) | `contact:<connection ip>` | fell back |
| WRONG secret + forged `203.0.113.99` | `contact:<connection ip>` | forgery rejected |
| NO secret + forged `203.0.113.50` | `contact:<connection ip>` | forgery rejected |

**The first row is the positive control and it is the point.** Without it, the three rejections
below it are indistinguishable from a feature that is simply broken -- every one of them would
read exactly the same if `getTrustedClientIp` returned `null` unconditionally. This is the same
trap that made 66.1-02's grant probe report a false pass until its service_role control exposed
it, and the same class as the `PGRST202` revoked-vs-absent tautology.

The second row matters independently: holding a valid secret does NOT buy the right to inject an
arbitrary rate-limit key. Authentication and validation are separate gates, and both run.

Note the secret was rotated once mid-test, on purpose. The first value was installed and
discarded unread, which left the positive case unprovable -- a live test of "valid secret" needs
the tester to hold the secret. Rotating let the positive control run, and both platforms were
re-installed from one variable in the same invocation, so they remain in sync.
