### Locked Decisions

- **D-01 - Postgres, not another service.** `check_rate_limit` becomes a SECURITY DEFINER RPC in

- **D-02 - Fails CLOSED, and there is no fail-open branch left.** Because the limiter and the
  write now share a domain, an unreachable database fails the write anyway. Delete the fail-open
  `catch` rather than porting it - a fail-open branch is exactly where the last outage hid.
- **D-03 - `_shared/rate-limit.ts` keeps its exported signature.** All five deployed edge
  functions (`apply-token`, `sign-lease-token`, `lease-signature`, `newsletter-subscribe`,
  `send-contact-email`) then inherit the change with no call-site edits.
- **D-04 - D5 is closed by fixing the BOUNDARY, not the key.** The `context` action is called
  only server-side by the RSC, so `getClientIp` returns the Vercel egress for 100% of genuine
  traffic. **Two previous attempts to fix this inside the edge function both failed** (see
  "Rejected alternatives"). The RSC forwards the true client address, authenticated by a
  constant-time shared-secret Bearer.
- **D-05 - The forwarding path is non-regressive BY CONSTRUCTION.** Absent secret, invalid
  secret, or missing header falls back to the connection address - today's exact behaviour. The
  change can never be worse than the status quo.
- **D-06 - Reuse the established secret pattern.** `supabase/functions/send-lease-reminders/index.ts:208`
  already does a constant-time shared-secret Bearer compare (`REMINDERS_INVOKE_SECRET`, mirrored
  into `app_config`). Follow it; do not invent a second mechanism.
- **D-07 - Delete the 800ms timeout.** It exists only to bound a hanging Upstash round trip. A
  same-region Postgres call is ~10-30ms.
- **D-08 - The outage must be observable.** `rateLimit()` already emits a structured
  `rate_limit_error`. Wire a Sentry alert on it. **Without this the phase merely resets the clock
  on the same silent failure** - that is the point of RATE-04, not a nice-to-have.
- **D-09 - The new trust boundary goes in the threat model.** If the forwarding secret leaks, an
  attacker can spoof their rate-limit identity. Same handling as `REMINDERS_INVOKE_SECRET`:
  Supabase function secret + Vercel env var, never in the repo.
- **D-10 - One atomic statement, no read-then-write.** `INSERT ... ON CONFLICT DO UPDATE`, matching
  the discipline `submit_rental_application` already uses. A check-then-act limiter is invisible
  to any single-threaded test - Phase 66 has a worked example of exactly that class.

## Summary

**The premise of the question is correct and it is the most important finding in this document.**
A naive `INSERT ... ON CONFLICT DO UPDATE` counter is a fixed window, and I measured the downgrade
rather than assuming it: against a limit of 10 per 10 seconds, a fixed window admitted **20
requests in a ~2 second span across the boundary**; the approximated sliding window admitted
**11**. That is exactly the 2x boundary burst, reproduced, on the same table and the same atomic
statement shape.

The good news is that Upstash's approximated sliding window **does** reproduce in one Postgres
statement, and it costs one extra unlocked `SELECT`. The trick is that the previous window's
counter is *frozen* - once the server clock has moved into window N, no session can still be
writing window N-1 - so reading it without a lock is stable, and the only value that needs
atomic read-modify-write is the current window's counter, which is precisely what
`INSERT ... ON CONFLICT DO UPDATE ... WHERE` provides.

I built the table and function in Postgres 17 and hammered them. Under 64 concurrent clients
making 2,560 attempts against a single key with a limit of 100, the recommended statement admitted
**exactly 100, three runs out of three**. A deliberately naive check-then-act limiter with the same
signature admitted **156, 159 and 161** under identical load - and admitted **exactly 100 when run
single-threaded**. That control is the whole point: it demonstrates that a single-threaded test
certifies a broken limiter as correct, which is the Phase 66 defect class this phase exists to
avoid repeating.

**Primary recommendation:** implement the approximated sliding window as a single
`INSERT ... SELECT ... WHERE <prev-guard> ON CONFLICT ... DO UPDATE ... WHERE <current-guard>
RETURNING`, with `lock_timeout` pinned on the function, `fillfactor = 70` on the table, and a
daily 3:25 UTC cleanup that loops bounded batches. Do not settle for a fixed window - the sliding
version is the same number of round trips and one extra index probe.

## The Recommended SQL

Everything below was executed against PostgreSQL 17.11 and behaved as documented. Pure ASCII.

### Table

```sql
create table public.rate_limit_counters (
  bucket_key    text        not null,
  window_index  bigint      not null,
  request_count integer     not null,
  expires_at    timestamptz not null,
  constraint rate_limit_counters_pkey primary key (bucket_key, window_index),
  constraint rate_limit_counters_request_count_check check (request_count >= 0),
  constraint rate_limit_counters_bucket_key_check
    check (length(bucket_key) between 1 and 512)
)
-- HOT updates need free space on the page to reuse. Measured: 99.6% of updates
-- were HOT at fillfactor 70 over 660k updates. Without headroom every increment
-- migrates the tuple to a new page and re-inserts both index entries.
with (fillfactor = 70);

create index rate_limit_counters_expires_at_idx
  on public.rate_limit_counters (expires_at);

-- This table's whole life is UPDATE churn. Default autovacuum thresholds are
-- tuned for tables that mostly grow, and would let dead tuples accumulate
-- between the once-daily sweep.
alter table public.rate_limit_counters set (
  autovacuum_vacuum_scale_factor  = 0.02,
  autovacuum_analyze_scale_factor = 0.05,
  autovacuum_vacuum_cost_delay    = 0
);

alter table public.rate_limit_counters enable row level security;

-- One policy per operation per role (CLAUDE.md), matching the
-- security_events_archive precedent in 20260306170000.
create policy "rate_limit_counters_select_service_role"
  on public.rate_limit_counters for select to service_role using (true);
create policy "rate_limit_counters_insert_service_role"
  on public.rate_limit_counters for insert to service_role with check (true);
create policy "rate_limit_counters_update_service_role"
  on public.rate_limit_counters for update to service_role using (true) with check (true);
create policy "rate_limit_counters_delete_service_role"
  on public.rate_limit_counters for delete to service_role using (true);

revoke all on table public.rate_limit_counters from public, anon, authenticated;
```

**No index on `request_count`.** That is load-bearing, not an omission: HOT updates require that
the updated column is not referenced by any index. `expires_at` is indexed but never updated, so
the index costs one entry per *insert* (a key's first request in a window) and nothing per
*update* (every subsequent request). The cost is amortised in the right direction.

### The function

```sql
create or replace function public.check_rate_limit(
  p_bucket_key   text,
  p_max_requests integer,
  p_window_ms    integer
)
returns table (
  allowed     boolean,
  limit_value integer,
  remaining   integer,
  reset_at_ms bigint
)
language plpgsql
security definer
set search_path = public
-- Bounds the hot-key contention case. Without this a flood on one key queues
-- callers behind the row lock until the statement or gateway times out; with
-- it, a contended call raises 55P03 in 250ms and the edge function denies.
-- Shedding load under flood is the correct fail-closed behaviour.
set lock_timeout = '250ms'
as $$
declare
  v_window_ms     bigint;
  v_now_ms        bigint;
  v_window_index  bigint;
  v_elapsed_ratio numeric;
  v_prev_count    integer;
  v_prev_weighted integer;
  v_new_count     integer;
  v_reset_ms      bigint;
begin
  if p_bucket_key is null or length(p_bucket_key) = 0 or length(p_bucket_key) > 512 then
    raise exception 'check_rate_limit: p_bucket_key must be 1..512 characters';
  end if;
  if p_max_requests is null or p_max_requests < 1 then
    raise exception 'check_rate_limit: p_max_requests must be >= 1';
  end if;
  if p_window_ms is null or p_window_ms < 1000 then
    raise exception 'check_rate_limit: p_window_ms must be >= 1000';
  end if;

  v_window_ms     := p_window_ms::bigint;
  v_now_ms        := (extract(epoch from clock_timestamp()) * 1000)::bigint;
  v_window_index  := v_now_ms / v_window_ms;
  v_elapsed_ratio := (v_now_ms % v_window_ms)::numeric / v_window_ms::numeric;
  v_reset_ms      := (v_window_index + 1) * v_window_ms;

  -- UNLOCKED READ, DELIBERATELY. The previous window is frozen: every backend
  -- reads the same server clock, so no session that can still be writing
  -- window N-1 exists once any session has entered window N. There is nothing
  -- for a lock to protect here.
  select c.request_count into v_prev_count
  from public.rate_limit_counters c
  where c.bucket_key   = p_bucket_key
    and c.window_index = v_window_index - 1;

  -- Upstash's weighting, reproduced exactly:
  --   floor((1 - elapsed_fraction) * previous_window_count)
  v_prev_weighted := floor((1 - v_elapsed_ratio) * coalesce(v_prev_count, 0))::integer;

  insert into public.rate_limit_counters as c
    (bucket_key, window_index, request_count, expires_at)
  select
    p_bucket_key,
    v_window_index,
    1,
    -- Needed as the "previous window" for all of window N+1, so it must
    -- outlive the end of N+1. Deterministic from the window boundary rather
    -- than from now(), unlike Upstash's PEXPIRE(window*2 + 1000).
    to_timestamp(((v_window_index + 2) * v_window_ms)::numeric / 1000.0)
  -- GUARD 1. Without this, the FIRST request of a new window is admitted
  -- unconditionally even when the weighted previous window already exceeds the
  -- limit -- the INSERT path never consults the limit at all. This is the
  -- single easiest bug to ship here. Verified: prev=100, limit=10, 5% into the
  -- new window -> allowed=false AND zero rows written.
  where v_prev_weighted < p_max_requests
  on conflict (bucket_key, window_index) do update
    set request_count = c.request_count + 1
    -- GUARD 2. Evaluated AFTER the row lock is taken, against the freshly
    -- re-read tuple. This is the atomicity.
    where c.request_count + v_prev_weighted < p_max_requests
  returning c.request_count into v_new_count;

  -- NULL means one of: guard 1 skipped the insert, or guard 2 rejected the
  -- update. Both are "denied", and neither wrote anything.
  if v_new_count is null then
    return query select false, p_max_requests, 0, v_reset_ms;
    return;
  end if;

  return query select
    true,
    p_max_requests,
    greatest(p_max_requests - (v_new_count + v_prev_weighted), 0),
    v_reset_ms;
end;
$$;

comment on function public.check_rate_limit(text, integer, integer) is
  'Approximated sliding-window rate limiter (RATE-01). Reproduces the weighting Upstash''s Ratelimit.slidingWindow used: floor((1 - elapsed_fraction) * previous_window_count) + current_window_count, compared against the limit. The decision and the increment are one statement: ON CONFLICT DO UPDATE takes the row lock before evaluating its WHERE, so concurrent callers serialize and no read-then-write window exists. A denied request writes nothing and burns no budget. service_role-only; the SECURITY DEFINER context is what lets edge functions call it without exposing a griefing surface to anon.';

revoke all on function public.check_rate_limit(text, integer, integer) from public, anon, authenticated;
grant execute on function public.check_rate_limit(text, integer, integer) to service_role;
```

**`p_window_ms` is `integer`, not `bigint`, on purpose.** I hit this during verification: with a
`bigint` parameter, a plain SQL literal (`check_rate_limit('k', 100, 3600000)`) fails function
resolution with *"No function matches the given name and argument types"*, because the literal
types as `integer`. PostgREST casts from JSON so the RPC path is unaffected either way, but every
psql-based test, RLS integration test, and manual `select` would need an explicit `::bigint`.
`integer` caps the window at ~24 days, which is three orders of magnitude above the largest window
in use (1 hour). Internal arithmetic still promotes to `bigint` via `v_window_ms`.

### Cleanup (pg_cron, 3:25 UTC)

```sql
create or replace function public.cleanup_rate_limit_counters()
returns integer
language plpgsql
security definer
set search_path = public
as $$
declare
  v_batch integer;
  v_total integer := 0;
  v_iter  integer := 0;
begin
  -- Bounded batches, matching cleanup_old_notifications / the Phase 66 sweep.
  -- The LOOP is the one deviation and it is deliberate: this table churns at
  -- minute granularity, so a single 10k batch per day cannot keep up under any
  -- load worth rate limiting. 50 iterations caps one run at 500k rows.
  loop
    v_iter := v_iter + 1;

    with due as (
      select bucket_key, window_index
      from public.rate_limit_counters
      where expires_at < now()
      limit 10000
      for update skip locked
    )
    delete from public.rate_limit_counters c
    using due
    where c.bucket_key   = due.bucket_key
      and c.window_index = due.window_index;

    get diagnostics v_batch = row_count;
    v_total := v_total + v_batch;

    exit when v_batch < 10000 or v_iter >= 50;
  end loop;

  raise notice 'cleanup_rate_limit_counters: deleted % row(s) in % batch(es)', v_total, v_iter;
  return v_total;
end;
$$;

comment on function public.cleanup_rate_limit_counters() is
  'Deletes expired public.rate_limit_counters rows. No archive table: these are ephemeral counters with no audit value, and expires_at is at most two windows past the row''s creation. Bounded at 10000 rows per batch with FOR UPDATE SKIP LOCKED, capped at 50 batches per run. service_role-only.';

revoke all on function public.cleanup_rate_limit_counters() from public, anon, authenticated;
grant execute on function public.cleanup_rate_limit_counters() to service_role;

select cron.unschedule('cleanup-rate-limit-counters') where exists (
  select 1 from cron.job where jobname = 'cleanup-rate-limit-counters'
);

select cron.schedule(
  'cleanup-rate-limit-counters',
  '25 3 * * *',
  $$select public.cleanup_rate_limit_counters()$$
);
```

**No archive table, and that is deliberate** - same reasoning shape as Phase 66's D-11c but a
different premise: these rows carry no evidentiary value whatsoever, and half of them are keyed on
IP addresses. Archiving would create a durable IP log out of data that is otherwise gone within
two windows. A reviewer pattern-matching on `cleanup_old_security_events` will want to add one.

## Why the statement is atomic

The proof is four sentences of PostgreSQL documentation plus one measurement.

1. > "`ON CONFLICT DO UPDATE` guarantees an atomic `INSERT` or `UPDATE` outcome; provided there is
   > no independent error, one of those two outcomes is guaranteed, even under high concurrency."
   [CITED: postgresql.org/docs/current/sql-insert.html]

2. > "Only rows for which this expression returns `true` will be updated, although **all rows will
   > be locked** when the `ON CONFLICT DO UPDATE` action is taken."
   [CITED: same]

3. > "Note that *condition* is **evaluated last, after a conflict has been identified as a
   > candidate to update**."
   [CITED: same]

4. > "Only rows that were successfully inserted or updated will be returned. For example, if a row
   > was locked but not updated because an `ON CONFLICT DO UPDATE ... WHERE` clause *condition* was
   > not satisfied, the row will not be returned."
   [CITED: same]

Read together: the lock is taken **before** the `WHERE` runs (2 + 3), so a concurrent caller waits,
then re-reads the committed tuple, then evaluates `c.request_count + v_prev_weighted <
p_max_requests` against a value that already includes every increment that beat it. There is no
interval between reading `request_count` and writing it in which another session can interleave -
which is the entire difference from a check-then-act limiter. And (4) is what makes
`RETURNING ... INTO v_new_count` a usable admit/deny signal: `NULL` means "locked, considered,
rejected, wrote nothing."

### Measured, not just argued

64 concurrent pgbench clients x 40 transactions = 2,560 attempts against **one** key, limit 100,
1-hour window (so the run cannot cross a boundary). The stored `request_count` equals the number
of admitted requests, because denied requests do not increment.

| Implementation | run 1 | run 2 | run 3 | Expected |
|---|---|---|---|---|
| Recommended (`ON CONFLICT ... WHERE`) | **100** | **100** | **100** | 100 |
| Naive check-then-act, same signature | 159 | 156 | 161 | 100 |
| Naive check-then-act, **1 client** | 100 | - | - | 100 |

The third row is the one that matters for the plan. The naive limiter over-admits by 56-61% under
concurrency and **passes cleanly when driven single-threaded**. Any acceptance test for RATE-01
that does not drive concurrent callers will certify a broken limiter, exactly as Phase 66's two
D5 attempts "shipped a passing test that certified a property the code did not have."

## Fixed vs sliding: the measurement

Same table, same atomic shape, only the algorithm differs. Limit 10 per 10,000ms. Both were
saturated at the end of window N, then re-probed immediately after the boundary.

| Algorithm | Admitted at end of N | Admitted just after boundary | Total in ~2s | Effective rate |
|---|---|---|---|---|
| Fixed window | 10 | **10** | **20** | **2.0x the limit** |
| Approximated sliding | 10 | **1** | **11** | **1.1x the limit** |

Capacity recovery across the following window, previous window saturated:

| Elapsed fraction of window | Requests admitted |
|---|---|
| 0.04 | 1 |
| 0.25 | 2 |
| 0.46 | 2 |
| 0.67 | 2 |
| 0.88 | 2 |

Smooth, ~10 per window, no cliff. That is the behaviour the submit path's 5/hour cap needs to
actually mean something.

### Accuracy characteristics, stated honestly

This is an **approximation, not a true sliding window**, and it inherits Upstash's exact
inaccuracy. It assumes the previous window's requests were uniformly distributed. Concretely:

- **Over-admits** when the previous window's traffic was back-loaded. If all 5 requests landed in
  the final second of the previous hour, then one second later the weighting discounts them to
  ~4 (`floor(0.9997 * 5)`), which is nearly right - but 30 minutes later it discounts them to 2
  while a true sliding window would still count all 5 (they are only 30 minutes old). Worst case
  the effective rate reaches roughly 1.5x the nominal limit over a window-and-a-half span.
- **Under-admits** when the previous window's traffic was front-loaded - it charges the caller for
  requests that have genuinely aged out.
- **Never** reaches the fixed window's clean 2x, which is the point.

A **true** sliding window requires storing individual request timestamps (one row per request, or
an array/`tstzrange` per key) and counting those newer than `now() - window`. Rejected:

- Storage becomes O(requests) rather than O(active keys). The `apply-context` bucket alone permits
  3,000 requests/min per listing; a true window would write 3,000 rows/min/listing instead of 1.
- The counting query is a range scan whose cost grows with the limit, versus a single index probe.
- It cannot be expressed as one atomic statement without either a lock or serializable retries.
- It buys accuracy that no requirement in RATE-01..04 asks for.

**Recommendation: the approximation.** It matches what production was nominally running before the
outage, so this phase restores the intended semantics rather than quietly redefining them.

## Lock contention on a hot key

Measured on PostgreSQL 17.11 in a 4-vCPU colima VM with **durable settings** (`fsync=on`,
`synchronous_commit=on`, `full_page_writes=on`) - the first pass with `fsync=off` reported
46,000-82,000 tps and is discarded as unrepresentative.

| Workload | Clients | TPS | Avg latency |
|---|---|---|---|
| ONE hot key | 1 | 8,732 | 0.115 ms |
| ONE hot key | 8 | 9,019 | 0.887 ms |
| ONE hot key | 32 | 8,280 | 3.865 ms |
| ONE hot key | 64 | 7,042 | 9.088 ms |
| ONE hot key | 128 | 4,920 | 26.019 ms |
| 100,000 distinct keys | 64 | 57,005 | - |

HOT update ratio on the hot key: **99.6%** (657,889 HOT of 660,458 updates) at `fillfactor = 70`.

**Reading these numbers.** Serialising on one row costs roughly 8x throughput versus spreading
across keys (7,042 vs 57,005 at 64 clients) - the contention is real and measurable. But the
ceiling sits at ~5,000-9,000 calls/second on laptop-grade hardware.

Now compare against what this surface plausibly sees. The busiest configured bucket is
`apply-context` at 3,000/min = **50/second**, and it is the only bucket that concentrates on a
single key by design (keyed on `tokenHash`, so one popular listing is one row). That is a **100x
margin** against the measured floor.

**So does contention matter? No - but not for the reason it first appears.** The ceiling is not
set by the allowed rate, because *denied* requests still take the row lock (a `WHERE`-false
`DO UPDATE` locks the row and writes nothing). Under a flood, the attack rate sets contention, not
the limit. The honest bound is therefore: to make the row lock the binding constraint an attacker
must sustain >5,000 requests/second **against a single listing token**. At that rate PostgREST
connection capacity and the Supabase gateway become the constraint long before the row lock does -
so the row lock is not the limiting factor, and tuning for it would be optimising the wrong thing.

`lock_timeout = '250ms'` is the mitigation that matters. It converts an unbounded queue into a
fast `55P03 lock_not_available`, which the edge function must treat as **deny** (fail closed).
Verified firing:

```
ERROR:  canceling statement due to lock timeout
CONTEXT:  while inserting index tuple (19,1) in relation "rate_limit_counters"
```

**Residual risk worth stating:** this is a genuine architectural cost of D-01 that Redis did not
have. A flood now consumes database capacity shared with every other query in the product. D-01
accepted that trade knowingly (same failure domain is the *point*), and `lock_timeout` bounds the
blast radius, but it is not zero. If a single-listing flood ever materialises, the correct answer
is the deferred Vercel WAF, not a change to this design.

## Storage growth and cleanup

Measured on a fresh 200,000-row table with realistic keys (`apply-context:` + 32-char hash):

| Component | Size |
|---|---|
| Heap | 19 MB |
| Indexes (pkey + expires_at) | 20 MB |

### Rows per key per window: exactly 1

Not one per request. That is the whole efficiency argument for the approximation.

### How many keys realistically exist

| Bucket (prefix) | Key | Window | Rows/window |
|---|---|---|---|
| `apply-context` | tokenHash | 60s | 1 per **active listing being viewed** |
| `apply-submit` | client IP | 3600s | 1 per **submitting IP per hour** |
| `lease-context` | tokenHash | 60s | 1 per lease link being viewed |
| `lease-context-ip`, `lease-document`, `lease-sign` | client IP | 60s | 1 per viewing IP |
| `lease-esign-email`, `lease-esign-finalize` | `user.id` | 60s | 1 per active owner |
| `contact`, `newsletter` | client IP | 60s | 1 per submitting IP |

Steady state for a product at this stage is **hundreds to low thousands of rows/day** - a rounding
error. The growth risk is entirely adversarial: a distributed scan against any IP-keyed 60s bucket
writes one row per distinct source address per minute. One million distinct addresses in a day is
~1M rows = **~206 MB**, still recoverable but no longer trivial.

### Why the cleanup function loops

The house idiom's single `LIMIT 10000` batch per daily run deletes 10,000 rows/day. Under the
adversarial case above that falls behind by two orders of magnitude and the table never drains.
The recommended function keeps 10,000-row batches with `FOR UPDATE SKIP LOCKED` (so lock hold time
and WAL pressure stay bounded, exactly as the idiom intends) but loops up to 50 times, capping one
run at 500,000 rows. Verified: 25,000 seeded expired rows were removed in **3 batches**, leaving 0.

**Daily at 3:25 UTC is sufficient** - not because a day's accumulation is small, but because
lookup cost is O(log n) on the primary key and stayed at 0.032 ms at 200k rows. The table can carry
a day of garbage without the hot path noticing. What it cannot carry is *unbounded* garbage, which
is what the loop prevents.

## Latency

**CONTEXT's "~10-30ms" (D-07) is right for the context path and optimistic for the submit path.**
The correction is not about Postgres - it is about *where the edge function runs*.

Verified components:

| Component | Value | How verified |
|---|---|---|
| RPC server-side execution | **0.96 ms** (cold), 0.115 ms (warm avg) | `EXPLAIN ANALYZE` + pgbench, this session |
| Index probe at 200k rows | 0.032 ms | `EXPLAIN ANALYZE`, this session |
| Edge function -> PostgREST -> Postgres round trip | **NOT VERIFIED** | Requires instrumenting a deployed function; not done this session |

The database work is negligible. The round trip is the whole cost, and it depends on a fact worth
flagging:

> Edge Functions "automatically execute in the region closest to the user making the request."
> [CITED: supabase.com/docs/guides/functions/regional-invocation]

The database is in **us-east-2** (CONTEXT, verified). PostgREST is *not* edge-distributed - it
serves from the project region. So the RPC's network cost is set by the distance from wherever the
function happened to execute to Ohio:

- **Context path** (`apply-context.ts:94`, server-originated from Vercel): the invoking IP is
  Vercel's, so the function executes near the Vercel region. `iad1` -> `us-east-2` is a short hop.
  **~10-30ms is credible here.**
- **Submit path** (`rental-application-form.tsx:125`, browser-originated): the function executes
  near the *applicant*. A California applicant lands the function on the US west coast, and the
  RPC then crosses the continent. **Realistically 60-90ms, not 10-30ms.**

I confirmed the edge is Cloudflare-fronted and geo-routed - a request from this machine (Texas)
returned `cf-ray: a2bc45a87c790c43-**DFW**`.

**What this means for the submit path, which makes one such call.** The submit path *already*
makes a cross-region PostgREST call (`submit_rental_application`). The limiter adds exactly one
more round trip of the same cost - so the marginal cost is "one more of what it already does,"
which is a far more honest framing than a raw millisecond figure. Against the status quo it is a
massive win regardless: CONTEXT measured the context action at **9.0-9.2s with two Upstash limiter
calls**, versus 0.28s with none. Replacing ~4.4s of hung Upstash per call with one same-continent
Postgres round trip is a two-orders-of-magnitude improvement even on the pessimistic estimate.

**Optional, and I do not recommend it for this phase:** `forceFunctionRegion` / the `x-region`
header can pin execution to `us-east-2`, trading browser->edge latency for edge->DB latency. Since
the submit path makes 2 DB calls and 1 client hop, pinning is probably a net win there - but it
changes routing behaviour for a whole function, is unmeasured, and is not required by RATE-01..04.
Record it as a follow-up, not a task.

**Delete the 800ms timeout regardless (D-07).** It was bounding an Upstash hang. Retaining it
would silently convert a slow-but-healthy cross-region RPC into a denial.

## The trusted-forwarding half

### Which header the RSC must read: `x-forwarded-for`

This is settled by Vercel's own documentation and the answer is unambiguous.

> **`x-forwarded-for`** - "The public IP address of the client that made the request. If you are
> trying to use Vercel behind a proxy, **we currently overwrite the `X-Forwarded-For` header and do
> not forward external IPs. This restriction is in place to prevent IP spoofing.**"
> [CITED: vercel.com/docs/headers/request-headers]

> **`x-vercel-forwarded-for`** - "This header is identical to the `x-forwarded-for` header. However,
> `x-forwarded-for` could be overwritten if you're using a proxy on top of Vercel."
> [CITED: same]

> **`x-real-ip`** - "This header is identical to the `x-forwarded-for` header."
> [CITED: same]

| Header | Set by | Client-controllable at the app? | Verdict |
|---|---|---|---|
| `x-forwarded-for` | Vercel edge, **overwritten** | **No** - explicitly overwritten to prevent spoofing | **Use this** |
| `x-vercel-forwarded-for` | Vercel edge | No | Equivalent; only differs if a proxy sits in front of Vercel |
| `x-real-ip` | Vercel edge | No | Equivalent; no advantage |

TenantFlow has no proxy in front of Vercel, so `x-forwarded-for` is correct. Reading
`x-vercel-forwarded-for` first with `x-forwarded-for` as fallback is defensible belt-and-braces and
costs nothing.

**The trap that will otherwise be shipped:** Vercel sets `x-forwarded-for` to a single client IP,
so if you defensively split on comma you must take the **FIRST** segment. That is the exact
**opposite** of the rule in `_shared/rate-limit.ts:117-131`, which takes the **LAST** segment - and
that rule is correct *there*, because at the Supabase edge the header is attacker-supplied and the
gateway appends the real address. Same header name, opposite correct answer, two files apart.
Both call sites need a comment saying why they differ, or someone will "fix" one to match the
other.

**Also note:** in Next.js 16 an RSC cannot reach a `Request` object, so `@vercel/functions`'
`ipAddress(request)` is unavailable. Use `headers()` from `next/headers` (async since Next 15).
The repo already imports `cookies` from that module in `src/lib/supabase/server.ts`; `headers` is
new but from the same place.

### The constant-time comparison in Deno

**Use the repo's existing `timingSafeEqualStr` from `supabase/functions/_shared/timing-safe.ts`.
Add no dependency.** D-06 already points at this and it is the right call for a reason worth
recording:

**Deno does not expose `crypto.subtle.timingSafeEqual`.** I checked the Deno `SubtleCrypto`
reference - the members are `generateKey`, `importKey`, `exportKey`, `wrapKey`, `unwrapKey`, `sign`,
`verify`, `digest`, `encrypt`, `decrypt`, `deriveBits`, `deriveKey`, and the non-standard
`supports()`. No `timingSafeEqual`.
[CITED: docs.deno.com/api/web/~/Crypto] `crypto.subtle.timingSafeEqual` is a **Cloudflare Workers**
extension, not a Web Crypto standard - which is very likely where the assumption came from.

So the feature-detect at `timing-safe.ts:29` always misses and the **XOR-loop fallback is what
actually runs in production today**. That is fine, and it is not a defect: the canonical Deno
alternative, `timingSafeEqual` from `jsr:@std/crypto`, carries the identical caveat - its own docs
call it "a best-effort constant-time comparison implemented in JavaScript. The V8 JIT compiler does
not provide formal constant-time guarantees."
[CITED: jsr.io/@std/crypto/doc/~/timingSafeEqual] Swapping to it would add a dependency and change
nothing about the guarantee. The existing helper's early length-mismatch return is also fine - the
secret's length is not secret.

**Correct one comment during the rewrite:** `timing-safe.ts:5-6` says "with an XOR-loop fallback
for portability across Deno runtimes that lack it," which reads as though the native path is the
normal one. It is the dead one.

### Header design

Do **not** overload `Authorization`. `lease-signature` already extracts a user JWT from it
(`identifier: user.id` at lines 207/389/594), and all five functions run `verify_jwt = false`, so
`Authorization` is semantically live. Use two dedicated headers:

- `x-tf-client-ip` - the forwarded address
- `x-tf-forward-secret` - the shared secret, compared with `timingSafeEqualStr`

This still satisfies D-06: the *mechanism* is unchanged (shared secret in Supabase function
secrets + the platform env, constant-time compare, never in the repo). Only the header slot
differs, and only because the canonical one is occupied.

**Validate the forwarded value even after the secret validates.** It becomes part of a database
key with a 512-character CHECK constraint. Cap length (an IPv6 address is at most 45 characters),
reject anything outside `[0-9a-fA-F:.]`, and take the first comma segment. A leaked secret should
buy an attacker a spoofed identity, not a key-space injection.

### The CORS trap

`_shared/cors.ts:30-31` sets:

```
"Access-Control-Allow-Headers": "authorization, x-client-info, apikey, content-type"
```

**Do not add the forwarding headers to that list.** The RSC's fetch is server-to-server and never
triggers a preflight, so it does not need them - and allowing them would let a *browser* send them,
which is precisely the spoofing vector the design exists to prevent. This needs an explicit comment
in `cors.ts`, because "the new header isn't in Allow-Headers" looks like an oversight to any
reviewer who does not know the omission is the control.

## Keeping the exported signature (D-03)

`_shared/rate-limit.ts` exports exactly two symbols. `RateLimitOptions` is declared at line 12
**without** `export`, so it is not part of the public surface.

| Export | Signature | Change |
|---|---|---|
| `getClientIp` | `(req: Request) => string` | Body gains a trusted-forward branch **in front of** the existing logic. Signature unchanged. |
| `rateLimit` | `(req: Request, options: RateLimitOptions) => Promise<Response \| null>` | Body swaps Upstash for `supabase.rpc`. Signature unchanged. |

`getClientIp`'s new shape - non-regressive by construction per D-05, because every failure path
falls through to today's exact code:

```ts
export function getClientIp(req: Request): string {
  const forwarded = req.headers.get("x-tf-client-ip");
  const presented = req.headers.get("x-tf-forward-secret");
  const expected = Deno.env.get("CLIENT_IP_FORWARD_SECRET");

  if (forwarded && presented && expected && timingSafeEqualStr(presented, expected)) {
    const candidate = normalizeForwardedIp(forwarded); // first segment, <=45 chars, charset-checked
    if (candidate) return candidate;
  }

  // Everything below is TODAY'S CODE, unmodified. Absent header, absent secret,
  // wrong secret, or malformed address all land here.
  const cfIp = req.headers.get("cf-connecting-ip");
  if (cfIp) return cfIp;
  // ...x-forwarded-for last segment, then "unknown"
}
```

**`cf-connecting-ip` being checked first is safe here - verified.** The existing comment
(lines 90-97) hedges on whether requests transit Cloudflare, and that hedge matters: if they did
not, an attacker could forge `cf-connecting-ip` and rotate rate-limit identities at will. They do.
`OPTIONS https://bshjmbshupiibfiewpxb.supabase.co/functions/v1/apply-token` returns `cf-ray`,
`cf-cache-status: DYNAMIC`, and `server: cloudflare`. Cloudflare sets `cf-connecting-ip` at its
edge and overwrites any inbound copy. The hedge can become an assertion, with that evidence
recorded.

### The client construction problem

`rateLimit(req, options)` receives no Supabase client and D-03 forbids adding a parameter. The
module must build its own, cached at module scope alongside the existing `cachedLimiters` map
(`rate-limit.ts:35`):

```ts
let cachedClient: SupabaseClient | null = null;
function getClient(): SupabaseClient {
  if (cachedClient) return cachedClient;
  const url = Deno.env.get("SUPABASE_URL");
  const key = Deno.env.get("SUPABASE_SERVICE_ROLE_KEY");
  if (!url || !key) throw new Error("Missing SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY");
  cachedClient = createAdminClient(url, key);

```

Both variables are **auto-injected into every Edge Function** by the platform - no secret needs
setting. [CITED: supabase.com/docs/guides/functions/secrets] Note that
`SUPABASE_SERVICE_ROLE_KEY` is documented under **"Legacy default secrets"** (the current pair is
`SUPABASE_SECRET_KEYS` / `SUPABASE_PUBLISHABLE_KEYS`). It still works and every existing function

future migration and should not be discovered by surprise.

CLAUDE.md's "No module-level Supabase client" rule targets the **frontend** hook layer (`src/hooks/`),
where per-request cookie scoping makes a shared client wrong. Edge functions have the opposite
constraint - a warm isolate should reuse its connection pool - and `_shared/supabase-client.ts`
exists precisely to be called this way. Worth a comment so the rule's absence is visibly
intentional.

**Service-role only, never anon.** If `check_rate_limit` were granted to `anon`, anyone holding the
publishable key could call it directly with another user's bucket key and exhaust their budget - a
one-line griefing DoS against the very surface this phase protects. The `revoke ... from anon,
authenticated` above is load-bearing, and `tests/integration/rls/anon-rpc-grants.rls.test.ts` is
the existing file that should assert it.

## Fail-closed error taxonomy (RATE-02)

D-02 says delete the fail-open `catch`. "Delete the catch" is not literally right - an uncaught
throw inside `rateLimit` propagates to each function's own handler and produces an inconsistent
mess across five functions. What RATE-02 requires is that **every** error path returns a denial
rather than `null`. Enumerate them so none is missed:

| Condition | Manifestation | Required behaviour |
|---|---|---|
| Database unreachable / DNS / TLS failure | `fetch` rejects | **Deny** (429 or 503) + emit `rate_limit_error` |
| PostgREST 5xx | `error` populated on the response | **Deny** + emit |
| Row-lock contention | `55P03 lock_not_available` | **Deny** + emit |
| Statement/gateway timeout | `57014` or a transport timeout | **Deny** + emit |
| Missing `SUPABASE_URL` / service key | `getClient()` throws | **Deny** + emit |
| Function missing (not yet migrated) | `PGRST202` "function not found" | **Deny** + emit - this is the deploy-ordering failure mode |
| Malformed / empty RPC payload | `data` is `[]` or `null` | **Deny** + emit - never treat "no row" as "allowed" |
| `allowed = false` | Normal denial | 429, existing headers, `rate_limit_hit` (not `rate_limit_error`) |

The last two are the ones a rewrite quietly gets wrong. `returns table` arrives through
supabase-js as an **array**; `data[0]?.allowed` on an empty array yields `undefined`, and
`if (!success)` on `undefined` happens to deny - but `if (result?.allowed === false)` would
**admit**. Prefer `.single()` (PostgREST returns an object and 406s on any other cardinality) or
an explicit shape check. Do not let admission be the default branch of anything.

**Deploy ordering follows directly:** the migration must be applied and verified in production
**before** any edge function carrying the new module is deployed, or every guarded surface returns
429 on `PGRST202`. This is the same blocking-gate shape as Phase 66's plan 66-06.

`rateLimit`'s existing error path is `console.error(JSON.stringify({...event: "rate_limit_error"...}))`

## Common Pitfalls

### 1. The INSERT path skips the limit check
**What goes wrong:** `INSERT ... ON CONFLICT DO UPDATE ... WHERE` only guards the **update**. The
first request of every new window has no conflict, so it inserts unconditionally - admitting one
request past a saturated previous window, every window, forever.
**Avoid:** `INSERT ... SELECT ... WHERE v_prev_weighted < p_max_requests` (guard 1 above).
**Detect:** seed a previous window at 10x the limit, call immediately after a boundary, assert
`allowed = false` **and** that zero rows exist in the new window.

### 2. A single-threaded test certifies a broken limiter
**What goes wrong:** measured above - naive check-then-act returns exactly 100/100 with one client
and 156-161 with 64.
**Avoid:** the RATE-01 acceptance test must drive genuine concurrency.
**Detect:** temporarily point the test at a deliberately naive implementation; if it still passes,
the test is worthless. (Cheap - the control function is ~15 lines.)

### 3. Taking the wrong `x-forwarded-for` segment
**What goes wrong:** LAST segment at Vercel is wrong; FIRST segment at the Supabase edge is
attacker-controlled. The two files need opposite rules.
**Avoid:** comment both; assert both directions in unit tests.

### 4. Adding the forwarding header to `Access-Control-Allow-Headers`
**What goes wrong:** makes the spoofing header browser-sendable, defeating the control.
**Avoid:** comment the omission in `cors.ts` as deliberate.

### 5. Treating an empty RPC result as "allowed"
**What goes wrong:** `returns table` yields an array; a missing/empty result read optimistically
admits everything - a silent product-wide no-op, i.e. the exact bug being fixed.
**Avoid:** `.single()` or explicit shape validation; deny by default.

### 6. Indexing `request_count`, or omitting `fillfactor`
**What goes wrong:** either kills HOT updates, turning every increment into a page migration plus
index churn on the hottest table in the database.
**Detect:** `select n_tup_upd, n_tup_hot_upd from pg_stat_user_tables where relname =
'rate_limit_counters'` - expect >95%. Measured 99.6%.

### 7. Adding an archive table to the cleanup job
**What goes wrong:** converts ephemeral counters - half of them IP-keyed - into a durable IP log.
**Avoid:** state the deviation in the migration header, as Phase 66's D-11c does.

### 8. Reintroducing a timeout around the RPC
**What goes wrong:** the 800ms bound existed for Upstash hangs. On a cross-region PostgREST call it
converts slow-but-healthy into denied.
**Avoid:** delete it (D-07); let `lock_timeout` handle the only case that needs bounding.

| Category | Applies | Control |
|---|---|---|
| V2 Authentication | Yes | Shared-secret Bearer for the forwarding boundary; `timingSafeEqualStr` |
| V3 Session Management | No | No sessions involved |
| V4 Access Control | Yes | `revoke ... from anon, authenticated` + `grant ... to service_role`; RLS with per-operation service_role policies |
| V5 Input Validation | Yes | `p_bucket_key` length CHECK + in-function guards; forwarded-IP charset/length validation |
| V6 Cryptography | Yes | Constant-time compare only; no hand-rolled crypto |
| V7 Error Handling / Logging | Yes | `rate_limit_error` -> Sentry (RATE-04); no raw `err.message` to clients (`_shared/errors.ts`) |
| V11 Business Logic | Yes | The rate limit itself - the anti-automation control |

### Known Threat Patterns

| Pattern | STRIDE | Mitigation |
|---|---|---|
| Forged `x-tf-client-ip` without the secret | Spoofing | Constant-time secret check; falls back to connection address |
| Leaked `CLIENT_IP_FORWARD_SECRET` | Spoofing | D-09: secret store only, never in repo; rotatable independently |
| Forged `cf-connecting-ip` | Spoofing | Cloudflare overwrites at its edge - **verified** via `cf-ray` / `server: cloudflare` |
| Browser sending the forwarding header directly | Spoofing | Header deliberately absent from `Access-Control-Allow-Headers` |
| `anon` calling `check_rate_limit` to burn a victim's bucket | DoS | Function revoked from `anon`/`authenticated` |
| Key-space injection via a long forwarded value | Tampering | 512-char CHECK + 45-char validation at the edge |
| Single-key flood -> row-lock queue | DoS | `lock_timeout = 250ms`, deny on `55P03` |
| Unbounded counter growth from a distributed scan | DoS | Bounded-batch daily cleanup, 500k rows/run |
| SQL injection via `bucket_key` | Tampering | Parameterised RPC; no dynamic SQL anywhere |

## Open Questions

1. **Does `rateLimit` return 429 or 503 when the database is unreachable?**
   - Known: it must deny (RATE-02). Both are defensible - 429 keeps the client contract uniform and
     reuses the existing `Retry-After` path; 503 is semantically honest and distinguishable in logs.
   - Unclear: whether any client branches on the status. `application-outcome.tsx:34` reasons about
     the submit limiter's hour window, so the applicant-facing copy may assume 429.
   - Recommendation: **429 with `Retry-After`**, plus the distinguishing `rate_limit_error` event
     for operators. Verify `application-outcome.tsx` before locking it.

2. **Should `bucket_key` store raw IPs or a hash?**
   - Known: `security_events.ip_address inet` and `user_errors.ip_address inet` already store raw
     IPs, so raw is the house precedent. Rows live at most two windows (<= 2 hours) and the table
     is service_role-only.
   - Unclear: whether transient IP retention needs privacy-notice treatment. It is operational
     security data with a short, bounded life, unlike `rental_applications.submitted_ip`.
   - Recommendation: **raw**, with a migration comment stating the retention bound. Hashing would
     make production triage impossible for a table whose entire purpose is abuse response.

3. **Should the `apply-context` ceiling be re-tuned in this phase?**
   - Known: CONTEXT says the 3,000/min per-listing ceiling is "sized for 'cannot distinguish
     callers', which will no longer be true" once RATE-03 lands.
   - Unclear: whether re-tuning is in scope. No RATE requirement mentions it.
   - Recommendation: **out of scope.** Land the mechanism, keep the number, re-tune once real
     per-client data exists. Changing the algorithm and the thresholds in one phase makes any
     regression un-attributable.

4. **Is `Sentry.init()` actually called in all five functions?** (A8)
   - Recommendation: the planner should grep before writing the RATE-04 task. If it is not, RATE-04
     needs an init task per function, which is real scope.
