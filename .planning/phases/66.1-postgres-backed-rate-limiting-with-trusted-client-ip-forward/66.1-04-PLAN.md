<objective>
Give the rate limiter a real per-client key on the one surface where it never had one, by fixing
the trust boundary rather than the key: the RSC forwards the platform-attested client address under
a shared secret, `getClientIp` verifies that secret in constant time before believing anything, and
`apply-token` consumes the verified address in a bucket that only exists when the address is
verified.

Purpose: D5 has been attempted twice inside the edge function and was wrong both times, because at
`apply-token` an attacker and an applicant are indistinguishable -- the context action is called
only server-side, so `getClientIp` returns the Next.js egress for 100% of genuine traffic and an
attacker reaches that same value by GETting the public page. No key that function can compute
separates them. The information that separates them exists exactly one hop earlier, at Vercel, and
this plan carries it across that hop with authentication instead of guessing at it.

Output: a pure trust decision the unit suite can execute, a forwarding branch in front of an
otherwise untouched `getClientIp`, a corrected comment in `timing-safe.ts`, a deliberate omission
recorded in `cors.ts`, and a consumer at `apply-token` gated on verification so the deploy ordering
cannot produce a window where behaviour changes.

**Nothing is provisioned or deployed here.** `CLIENT_IP_FORWARD_SECRET` is set on both sides and the
functions are redeployed in 66.1-05. Until then every path in this plan resolves to today's exact
behaviour, which is the whole design (D-05).
</objective>

<which_header_and_why_the_obvious_choice_would_have_been_wrong>
**This is the decision the entire plan rests on. It is settled from Vercel's own documentation, not
inferred, because guessing here reproduces D5 in a new location.**

Source: `https://vercel.com/docs/headers/request-headers` (Vercel docs, `last_updated: 2025-12-13`),
sections `x-forwarded-for`, `x-vercel-forwarded-for`, `x-real-ip`. Quoted:

- **`x-forwarded-for`** -- "The public IP address of the client that made the request. If you are
  trying to use Vercel behind a proxy, we currently **overwrite** the `X-Forwarded-For` header and
  **do not forward external IPs**. This restriction is in place **to prevent IP spoofing**." A
  sub-section, `Custom X-Forwarded-For IP`, notes that only **Enterprise** customers with a purchased
  **Trusted Proxy** permission can have their custom `X-Forwarded-For` honoured.
- **`x-vercel-forwarded-for`** -- "This header is identical to the `x-forwarded-for` header.
  **However, `x-forwarded-for` could be overwritten if you're using a proxy on top of Vercel.**"
- **`x-real-ip`** -- "This header is identical to the `x-forwarded-for` header."

**What this settles, and what it refutes.** Vercel OVERWRITES `x-forwarded-for`; it does not append
to a client-supplied value. So the widely-repeated warning that "the first XFF segment is
attacker-controlled" -- which is true at almost every other edge, and is true at the Supabase edge in
this very repo -- is **false at Vercel specifically**, and by explicit design. An inbound
`x-forwarded-for: 1.2.3.4` from a client is discarded before the function runs.

**Chosen: `x-vercel-forwarded-for`, falling back to `x-forwarded-for`.** `x-vercel-forwarded-for` is
documented as the value that survives even the one case where `x-forwarded-for` can be displaced -- a
proxy sitting on top of Vercel. It is strictly the more attested of the two and it costs one extra
`get()`. The fallback exists because the docs do not guarantee `x-vercel-forwarded-for` on every
runtime and a missing header must not silently disable the mechanism forever; the ordering means
that if this project ever acquires a proxy-on-top or a Trusted Proxy permission, the attested value
still wins without a code change.

**Rejected: `x-real-ip`.** Documented as "identical to the `x-forwarded-for` header", so it inherits
the same overwrite caveat and adds zero attestation over the header we already read. Choosing it
would look like a decision while being a coin flip.

**Rejected: any convenience accessor** (`@vercel/functions`' `ipAddress()`, or a framework helper).
The header precedence would then live in a dependency instead of in the diff, and the entire point of
this section is that the precedence must be reviewable. We read headers explicitly.

**Rejected: "take the first comma segment".** The docs describe each of these as "**the** public IP
address of the client" -- singular. A comma in the value therefore contradicts the documented
contract, and picking an end of a list Vercel says it does not produce is exactly the kind of
convenient reading that shipped D5 twice. **So a multi-segment value is REFUSED, not parsed:** the
RSC forwards nothing and the edge falls back to the connection address. Refusing to guess is
fail-closed to today's behaviour, costs nothing, and cannot be wrong in either direction.

**This supersedes the outline.** `66.1-PLAN-OUTLINE.md` (per-plan note for 66.1-04) instructs "at
Vercel take the **FIRST** segment". Its underlying claim -- that Vercel overwrites XFF to prevent
spoofing -- is confirmed correct by the citation above, but the instruction built on it is not what
this plan implements: we prefer the more attested header and refuse multi-segment values entirely.
Follow this plan, not that line.

**Still unproven here, and it belongs to 66.1-05:** that production actually populates
`x-vercel-forwarded-for` for an RSC render, and that an end-to-end forged `x-forwarded-for` on a real
request to `/apply/[token]` does not reach the bucket key. Both need a deployed function and a live
request. 66.1-05 already performs a live RATE-03 confirmation; this plan's SUMMARY must hand it the
explicit forged-header case rather than assuming the generic check covers it.
</which_header_and_why_the_obvious_choice_would_have_been_wrong>

<the_constant_time_compare_was_audited_not_assumed>
D-06 says reuse the `send-lease-reminders/index.ts:208` pattern. Read before copying, per the
instruction, and here is what the read found.

**The mechanism is sound; reuse it verbatim.** `_shared/timing-safe.ts`'s `timingSafeEqualStr`
encodes both operands with `TextEncoder`, returns `false` on a length mismatch, and otherwise
accumulates `d |= a[i] ^ b[i]` across the full length before comparing `d === 0`. There is no
early return inside the loop, so the comparison time does not depend on where the first differing
byte is. That is the property that matters.

**The length-mismatch early return at line 23 is correct, not a leak.** It is explicitly justified in
the file ("the secret's length is not itself secret"), it matches all three existing inline helpers,
and Node's own `crypto.timingSafeEqual` refuses unequal-length inputs outright rather than comparing
them. The secret here is a fixed-length value the operator generates once; its length carries no
usable information.

**One thing in that file is UNVERIFIED, and the fix is to stop asserting it -- not to assert the
opposite.** Lines 3-6 and 25-29 present `crypto.subtle.timingSafeEqual` as the primary path with the
XOR loop as "a fallback for portability across Deno runtimes that lack it".

`crypto.subtle.timingSafeEqual` is a **real non-standard extension**. Deno documents it -- "compares
array buffers or data views in a way that isn't prone to timing based attacks ... likely some form of
timing safe equality will make its way to the WebCrypto standard, see `w3c/webcrypto#270`, but until
that time `timingSafeEqual()` is provided" -- and Cloudflare's workerd implements the same extension.
So the original comment may well be accurate.

**What could not be settled from documentation:** whether Deno's **global** `crypto.subtle` exposes
it, or only the `std/crypto` wrapper type (`StdSubtleCrypto`) does. The std docs describe an interface
that EXTENDS `SubtleCrypto`, which is weak evidence that the addition belongs to std rather than to
the global -- and Supabase Edge Functions use the global. That is the entire state of the evidence,
in both directions, and it does not resolve.

**There is no defect here to fix.** Feature detection with a constant-time fallback is sound whichever
branch executes: both paths are constant-time, so correctness does not depend on which one runs. The
only thing wrong is a description that claims to know something nobody has checked.

**So the comment must record the uncertainty and stop.** An executor who "corrects" this to say the
XOR loop is the live path would ship a second confident-and-possibly-wrong sentence into the file,
which is strictly worse than the first one -- it launders an unverified claim through a phase whose
entire thesis is that confidently wrong comments are load-bearing defects. `_shared/errors.ts`
claimed it "handles missing DSN gracefully" over a call that never transmitted anything, and that
sentence is why 16 functions went unmonitored for months. Repeating that mistake inside the phase
that exists to remove it is not a small error.

**Deliberate deviation from `send-lease-reminders`, stated so it does not read as an oversight:**
that call site compares the full `Authorization` header against the literal `` `Bearer ${secret}` ``.
This plan uses a dedicated header, `x-tf-forward-secret`, and compares its raw value against the raw
secret with no `Bearer` prefix. Two reasons: `Authorization` is already carrying user JWTs at
`lease-signature`, so overloading it creates a real collision; and once the header is not
`Authorization`, `Bearer ` is a constant on both sides of a constant-time compare -- ceremony, not
security. The mechanism reused is `timingSafeEqualStr`, which is the part D-06 is about.
</the_constant_time_compare_was_audited_not_assumed>

<the_3000_per_minute_ceiling_decision>
**Decision: KEEP 3,000/min on `prefix: "apply-context"`, keyed on `tokenHash`. Rewrite its
justification. Add a separate, trust-gated per-client bucket beside it.**

The orchestrator's instruction was to either re-scope it now or record explicitly why it stays and
what would change that. Here is the record.

**Why the number stays.** The tokenHash bucket is a **per-listing aggregate capacity ceiling**. It
bounds total load on one listing regardless of how many distinct clients generate it. A per-client
bucket does not replace that: a thousand distinct addresses each staying under their own limit still
sum to a thousand times the load, and the ceiling is the only thing that bounds the sum.
`apply-token-contract.test.ts:441-446` already parses this number and asserts `>= 1000` specifically
so nobody tightens it back into the lockout range; that assertion remains correct and untouched.

**What was obsolete, and is being fixed.** The *justification* around it, not the number.
`apply-token/index.ts` currently carries a comment block saying "WHERE THE REAL PER-CLIENT LIMIT
BELONGS: `src/proxy.ts`, which sees the actual client address before the RSC ever runs ... recorded
in deferred-items.md rather than bolted on here", and `apply-token-contract.test.ts:412-437` records
"an attacker and an applicant are INDISTINGUISHABLE at this function. No key it can compute
separates them." Both were true *while the address available to that function was the shared
egress*. RATE-03 changes the input, not the reasoning: a verified forwarded address is a key the
function can now compute that does separate them. Leaving those two comments in place is exactly the
"obsolete justification left in place is how the next reviewer concludes the number is deliberate"
failure -- worse here, because a future reader would conclude per-client limiting is still
impossible at this function when the mechanism to do it is sitting three lines above.

**What is added.** A second bucket, `prefix: "apply-context-client"`, `maxRequests: 60`,
`windowMs: 60_000`, `identifier: <verified forwarded address>`, entered **only** when
`getTrustedClientIp(req)` returns non-null.

- **The gate is what makes it safe to merge before 66.1-05.** With no secret provisioned, no address
  is ever verified, the branch is never entered, and the context action performs exactly the one
  limiter call it performs today. Ungated, this bucket would key on the Vercel egress for 100% of
  genuine traffic and become a product-wide 60/min cap on every apply page load -- which is the
  precise defect that got the old 300/min address-only ceiling removed.
- **The prefix is deliberately NOT `apply-context-ip`.** `apply-token-contract.test.ts:450` asserts
  `expect(CODE).not.toContain('prefix: "apply-context-ip"')` to keep the ungated address-only
  ceiling from returning. **That assertion is kept, unchanged, and still passes** -- a distinct
  prefix means the old ungated control stays forbidden forever while the new gated one is pinned
  separately. No existing assertion is relaxed anywhere in this plan.
- **Why 60/min.** One context call per page load. A human reloading a listing page faster than once
  per second, sustained for a minute, is not a human; and clients sharing a carrier NAT or a
  corporate egress still sit far below it on a single niche listing. The number is per verified
  client, so crawlers and link-preview bots -- the traffic the 3,000 ceiling was sized for -- each
  land in their own bucket rather than the shared one.
- **Cost.** When trusted, the context action makes two limiter RPCs instead of one, ~10-30ms each
  against a same-region Postgres. It is replacing a path that measured 9.0-9.2s on 2026-08-09.

**What would change this decision:** production evidence that a single listing legitimately exceeds
3,000 context calls/min (raise the ceiling), or evidence that verified per-client traffic routinely
approaches 60/min (raise that number). Neither is guesswork-resolvable now; 66.1-05's live check is
the first opportunity to see real numbers.

**Handoff:** `deferred-items.md` is owned by 66.1-05. Its D5 entry, and its note that per-client
limiting is deferred to `src/proxy.ts`, are both superseded by this plan and must be reconciled
there. The SUMMARY carries that instruction.
</the_3000_per_minute_ceiling_decision>
