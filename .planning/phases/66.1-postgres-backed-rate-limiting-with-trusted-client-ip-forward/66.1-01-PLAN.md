<the_defect_this_plan_exists_to_prevent>
`INSERT ... ON CONFLICT DO UPDATE ... WHERE` guards **only the update path**. The first request of
each new window has no conflict, so that `WHERE` never evaluates.

A one-guard version therefore admits one request past a saturated previous window **at every window
boundary, forever** -- and it reads as completely correct in review, because the `WHERE` clause a
reviewer looks for is present. It is also invisible to a sequential test.

The correct statement has BOTH:

- **GUARD 1** -- `where v_prev_weighted < p_max_requests` on the `insert ... select`
- **GUARD 2** -- `where c.request_count + v_prev_weighted < p_max_requests` on the `do update`

Research verified GUARD 1's effect directly: prev=100, limit=10, 5% into the new window ->
`allowed = false` **and zero rows written**.

Second, related trap: **a single-threaded test certifies a broken limiter.** Research measured the
control. A naive check-then-act limiter with the identical signature admitted:

| Implementation | run 1 | run 2 | run 3 | Expected |
|---|---|---|---|---|
| Recommended (two-guard, one statement) | 100 | 100 | 100 | 100 |
| Naive check-then-act, 64 clients | 159 | 156 | 161 | 100 |
| Naive check-then-act, **1 client** | 100 | - | - | 100 |

Row 3 is the one that matters. Any RATE-01 test that does not drive genuine concurrency passes
against a limiter that over-admits by ~60%. Phase 66 shipped two tests that certified properties
the code did not have; this is the same shape.
</the_defect_this_plan_exists_to_prevent>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `anon` / `authenticated` -> PostgREST -> `public.*` | Any browser can reach PostgREST with the publishable key. Every function in `public` is callable by whoever holds an EXECUTE grant, and PostgreSQL auto-grants EXECUTE to PUBLIC at creation, which `anon` inherits. |
| Edge function (service_role) -> `check_rate_limit` | The only intended caller. Trusted, but its `p_bucket_key` argument is derived from attacker-influenced input (client IP, token hash) and crosses into a database key. |
| pg_cron (service_role) -> `cleanup_rate_limit_counters` | No caller identity; grant discipline, not a `auth.uid()` guard, is what keeps it off every other code path. |
| Unbounded internet -> one hot bucket key | A flood concentrates on a single row's lock. Denied requests take that lock too. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-66.1-01 | Denial of Service (control bypass) | `check_rate_limit` INSERT path | mitigate | **The phase's central threat.** GUARD 1 (`where v_prev_weighted < p_max_requests`) on the `insert ... select`. Enforced by Task 1's line-anchored grep for both guards and by Task 2's boundary test asserting `allowed === false` **and** zero rows written. |
