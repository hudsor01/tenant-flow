<what_this_plan_is_actually_fixing>
Two independent silent failures, both of which certify themselves as healthy.

**1. The limiter fails open.** `rate-limit.ts:184-196` catches every error and returns `null`,
which every one of the 11 call sites reads as "not limited, proceed". When Upstash's free database
was reaped, the limits stopped existing and the only symptom was latency. Measured 2026-08-09:
`apply-token` context (two limiter calls) took 9.0-9.2s against 0.28s for an action with none.

**2. `Sentry.captureException` has never transmitted.** Verified by grep, not recollection:

- `Sentry.init` appears exactly ONCE in all of `supabase/functions/` -- `stripe-webhooks/index.ts:32`.
- `_shared/errors.ts` imports `@sentry/deno` and calls `Sentry.captureException` at lines 35 and 72,
  and contains no init of its own.
- **Seventeen** functions import `_shared/errors.ts`: apply-token, auth-email-send,
  download-documents-zip, export-report, export-user-data, generate-pdf, lease-signature,
  n8n-blog-ingest, newsletter-subscribe, resend-webhook, send-contact-email, send-lease-reminders,
  sign-lease-token, stripe-billing-portal, stripe-cancel-subscription, stripe-checkout,
  stripe-webhooks.

So the standard house error path has been capturing into an unbound client in 16 of those 17
functions since it was written. Not just the limiter -- every handled error in nearly every edge
function.

**What made it durable is the file's own prose.** `errors.ts:2` says "Logs full error details to
Sentry + console.error". The inline comment above line 35 says "Sentry logging (handles missing DSN
gracefully)". Both are true of a client that was initialised without a DSN and false of a client
that was never initialised at all. The comment is why nobody looked. It is part of the defect and
it is corrected in the same task as the mechanism -- a repaired mechanism sitting under a comment
that already claimed it worked is exactly how this recurs.

**Why fixing `errors.ts` is in scope and not scope creep:** RATE-04 requires the outage to be
observable via a Sentry alert on `rate_limit_error`. Wiring an alert to a call that cannot transmit
would ship a monitoring control that reports healthy because it is not running -- the precise
defect class this phase exists to eliminate. RATE-04 is unsatisfiable without it.

**Where the init goes, and why not in `rate-limit.ts`:** in `_shared/errors.ts`, where the
`captureException` calls already are. One guarded once-only binding there repairs all 17 functions
rather than the 5 rate-limit callers, and it edits no call sites, so D-03 survives intact. Putting
the init in `rate-limit.ts` would repair 5 functions and leave 11 broken for no reason.

**Scope line, hold it:** the init plus the two lying comments. No re-plumbing of error shapes, no
touching the 17 call sites, no DSN provisioning, no removal of the now-redundant module-level init
in `stripe-webhooks/index.ts` (leaving it costs a 6th redeploy and the guard handles it).
</what_this_plan_is_actually_fixing>

    A dependency-free leaf in the exact sense `application-guards.ts` is one: **zero imports and
    zero runtime-global references** -- no `Deno`, no `fetch`, no `Response`, no `console`. That
    constraint is the whole point and must be stated in the file header, because it is what lets

    Exports:

    - `RATE_LIMIT_ERROR_CLASSES`, a readonly tuple of the seven error classes, one per non-normal
      row of the RESEARCH taxonomy: `db_unreachable`, `postgrest_5xx`, `lock_contention`,
      `statement_timeout`, `missing_env`, `function_missing`, `malformed_payload`. Plus the derived
      `RateLimitErrorClass` union type. Seven error classes plus the normal `allowed = false` row is
      the 8-row table.
    - `ERROR_RETRY_AFTER_CAP_SEC = 60`.
    - `RateLimitRpcOutcome`, a discriminated union describing everything the caller can hand over:
      `{ kind: "ok"; data: unknown }`, `{ kind: "postgrest_error"; code: string | null; status: number | null; message: string }`,
      `{ kind: "thrown"; message: string }`, `{ kind: "missing_env"; message: string }`.
      `data` is deliberately `unknown` -- the leaf validates the shape rather than trusting a type
      assertion, which is the only thing that makes the malformed-payload row testable.
    - `RateLimitDecision`: `{ allowed: boolean; errorClass: RateLimitErrorClass | null; limit: number; remaining: number; resetAtMs: number; retryAfterSec: number }`.
    - `decideRateLimit(outcome: RateLimitRpcOutcome, options: { maxRequests: number; windowMs: number; nowMs: number }): RateLimitDecision`.

    `nowMs` is a parameter, not `Date.now()`, so the leaf stays global-free and the tests are
    deterministic.

    **The one invariant that governs every branch:** `allowed` is `true` if and only if the
    validated row's `allowed` field is strictly `=== true`. Write that as a comment above the
    return. Admission is never the default branch of anything, never the `else`, never what happens
    when a check falls through. Pitfall 5 is that `data?.allowed` on an array is `undefined` and
    `undefined !== false`, so an optimistic read admits everything -- a silent product-wide no-op,
    i.e. the exact bug this phase exists to fix.

    Shape reading, in a helper `readVerdictRow(data: unknown)`. It must accept **both** the
    `.single()` object form and the bare `returns table` array form, and return `null` for anything
    else. `rate-limit.ts` uses `.single()`, but 66.1-01's RLS test reads the array form, and a
    future edit that drops `.single()` must degrade to correct behaviour rather than to admission.
    A row is valid only when `allowed` is a boolean and `limit_value` / `remaining` / `reset_at_ms`
    are finite numbers. Anything else -- `null`, `undefined`, `[]`, an object missing a field, a
    string where a number belongs -- is `null`, which maps to `malformed_payload` and denies.

    Classification:

    - `kind: "missing_env"` -> `missing_env`.
    - `kind: "thrown"` -> `db_unreachable`. Every throw out of a `fetch`-backed supabase-js call is
      a transport failure: DNS, TLS, connection refused, abort. Do not pattern-match the message to
      subdivide it; the class exists to route the event, and a message-sniffing branch that fails to
      match must not become a path that admits.
    - `kind: "postgrest_error"` -> by `code`: `PGRST202` -> `function_missing` (the deploy-ordering
      failure mode -- the migration is not applied), `55P03` -> `lock_contention`, `57014` ->
      `statement_timeout`, anything else -> `postgrest_5xx`. `status` is carried for the log only.
    - `kind: "ok"` with an unreadable row -> `malformed_payload`.
    - `kind: "ok"` with a valid row and `allowed === true` -> allowed, `errorClass: null`, carrying
      the row's `limit_value` / `remaining` / `reset_at_ms`.
    - `kind: "ok"` with a valid row and `allowed === false` -> denied, `errorClass: null` (this is
      the normal denial; the caller logs `rate_limit_hit`, not `rate_limit_error`).

    `retryAfterSec`: for a normal denial, `Math.max(1, Math.ceil((resetAtMs - nowMs) / 1000))`, from
    the row. For every error class, `Math.min(ERROR_RETRY_AFTER_CAP_SEC, Math.max(1, Math.ceil(windowMs / 1000)))`
    with `resetAtMs = nowMs + retryAfterSec * 1000`. Comment the cap: an error is not a real limit
    breach, so echoing `apply-submit`'s one-hour window at an applicant because the database
    blipped punishes them for our outage, while a 1-second value invites a retry storm into an
    already-sick database. 60s is the compromise, and the header is advisory in either case --
    the denial is what enforces.

| T-66.1-11 | Denial of Service (control bypass) | A later refactor reintroducing fail-open | mitigate | Three independent gates, because this is the defect that already happened once: `grep -c "return null" === 1` over `rate-limit.ts` (Task 2 verify); a balanced-brace assertion that no `catch` block contains `return null` (Task 3); and an executed Vitest case asserting `decideRateLimit({ kind: "thrown" })` denies (Task 1). | T-66.1-12 | Repudiation / Information Disclosure | The limiter's own database error being swallowed | mitigate | Every error class routes through `captureWebhookError` with `event: "rate_limit_error"`, which writes the structured `console.error` AND calls `Sentry.captureException`. Without both halves this row is unmitigated no matter how many capture calls exist. |
| T-66.1-13 | Repudiation | Handled errors invisible across 16 functions | mitigate | **The reason T-66.1-12 could not have worked before.** `Sentry.init` ran only in `stripe-webhooks/index.ts:32`, while 17 functions import `_shared/errors.ts` and call `captureException` through it -- so every handled error in 16 functions has been captured into an unbound client since the module was written. | T-66.1-14 | Denial of Service | Attacker forces the error path to obtain fail-open behaviour | mitigate | Structurally impossible after this plan: every error class returns 429, so forcing an error is strictly *worse* for the attacker than a normal request. That is bounded by the shared failure domain (D-01): to break the limiter they must break the database, which fails the guarded write anyway, so the limiter adds no new availability surface. The `55P03` path is the cheapest error to force and is capped at 250ms of database time by `lock_timeout`. |
| T-66.1-15 | Denial of Service | Lock contention driven by DENIED requests | accept | Denied requests take the row lock too, so **the attack rate sets contention, not the configured limit** -- a 5/hour bucket under a 5,000 req/s flood takes 5,000 lock acquisitions per second, not 5 per hour.
