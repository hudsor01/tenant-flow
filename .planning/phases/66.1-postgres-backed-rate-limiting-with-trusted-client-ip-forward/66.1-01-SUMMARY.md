## Accomplishments

### Task 1 -- `supabase/migrations/20260816010000_rate_limit_counters.sql` (415 lines, pure ASCII)

Transcribed verbatim from RESEARCH's `## The Recommended SQL`, comments included:

- `public.rate_limit_counters` -- composite PK `(bucket_key, window_index)`, `fillfactor = 70`, index on `expires_at` only, autovacuum overrides, RLS on, four per-operation service_role policies (no `for all`), `revoke all on table ... from public, anon, authenticated`.
- `public.check_rate_limit(p_bucket_key text, p_max_requests integer, p_window_ms integer)` -- `security definer`, `set search_path = public`, `set lock_timeout = '250ms'`, three input raises, unlocked previous-window read, Upstash weighting, and the single `insert ... select ... where` / `on conflict do update ... where` / `returning ... into` statement carrying **GUARD 1** and **GUARD 2**.
- `public.cleanup_rate_limit_counters()` -- 10k-row batches, `for update skip locked`, hard cap of 50 iterations, `get diagnostics` + `raise notice`.
- Revoke-before-grant on both functions; `cron.unschedule ... where exists` guard then `cron.schedule('cleanup-rate-limit-counters', '25 3 * * *', $$select public.cleanup_rate_limit_counters()$$)`.

Header block states the four things the plan required: not applied here; the two guards are the design (with the 156/159/161-vs-100 control and the test file that catches a regression); no archive table and why consistency with the sibling retention jobs would be the bug; and that `public.check_rate_limit` is not `stripe.check_rate_limit`.

### Task 2 -- `tests/integration/rls/rate-limit-concurrency.rls.test.ts` (434 lines)

64 workers via `Promise.all` x 40 sequential attempts = 2,560 attempts against a limit of 100, over a 1-hour window, three runs on fresh uuid keys. Each run asserts `admitted === LIMIT`, `peakInFlight >= 32`, and the stored `request_count === LIMIT`. Plus: the client-side check-then-act control asserting `controlAdmitted > LIMIT` strictly with a failure message explaining that an equal result invalidates every other assertion in the file; the GUARD 1 boundary case asserting **both** `allowed === false` and an exact head-count of 0 rows at the current window index; a denied-do-not-increment case; and the three input-validation raises. Admission is read as `Array.isArray(data) && data[0]?.allowed === true`. All keys namespaced `test:rate-limit-concurrency:` + `randomUUID()`, torn down in `afterAll` with a re-query proving 0 remain.

### Task 3 -- `tests/integration/rls/anon-rpc-grants.rls.test.ts`

Both functions added to `REVOKED_FROM_ANON` and `REVOKED_FROM_AUTHENTICATED` with argument objects matching the migration's parameter names. Added the service-role positive control in its own `describe.skipIf` -- `check_rate_limit` must return `error === null` and an admitted first row, `cleanup_rate_limit_counters` must return `error === null` and a number -- because `REVOKED_CODES` accepts `PGRST202`, which is also what PostgREST returns for an **absent** function. The file already documented that tautology for `log_lease_signature_activity`; a comment now states exactly what the RATE-02 pins degrade to when the control skips.

## WHAT IS NOT PROVEN HERE

Stated plainly rather than implied away:

- **The migration was NOT applied.** No `mcp__supabase__apply_migration`, no Management API call, no `bun run db:types`. **No statement in this file has ever been parsed by a PostgreSQL server.** Plan 66.1-02 is the owner-gated apply and is the first parse.
- **SQL syntax validity and function resolution are unverified.** The Task 1 gate is a structural/text assertion. It proves both guards are present, line-anchored and unique; it cannot prove the file compiles.
- **Whether cron minute :25 is still free is unverified.** That reading is from 2026-08-06 (assumption A5, medium risk). 66.1-02 must re-query `cron.job` before applying.
- **Neither test was run, deliberately.** `bun run test:integration` hits production and `public.check_rate_limit` does not exist there yet, so every RPC call returns `PGRST202`. A green integration run at this point would mean an assertion had been weakened. They are authored-but-unrun by design; 66.1-02 runs them green against production as its gate.
- **The measured limiter behaviour (100/100/100 at 64 clients) is RESEARCH's measurement against PostgreSQL 17.11, not a measurement taken in this plan.** This plan reproduces the statement that produced it.

## Deviations from Plan

Four. Two mechanical typecheck fixes, and two judgement calls in the state-update step:

**1. [Rule 3 - Blocking] `noUncheckedIndexedAccess` rejected two direct `data[0].request_count` reads**
- **Found during:** Task 2, first `bun run typecheck` (TS2532 at two sites in `rate-limit-concurrency.rls.test.ts`).
- **Fix:** bound `data[0]` to a local first and guarded it (`const row = Array.isArray(data) ? data[0] : undefined`) instead of indexing inline. The strict admission read `data[0]?.allowed === true` in `isAdmitted()` was left exactly as specified -- it typechecks because `Array.isArray` narrows `unknown` to `any[]` -- so the plan's grep target and the pitfall-5 semantics are unchanged.
- **Commit:** f1cb8886c

**2. [Rule 3 - Blocking] `REVOKED_FROM_AUTHENTICATED` required an optional `args`**
- **Found during:** Task 3. Its element type declared `args` as required, but `cleanup_rate_limit_counters` takes no arguments.
- **Fix:** widened to `args?: Record<string, unknown>` and made its loop use the same `fn.args ? rpc(name, args) : rpc(name)` form the anon loop already used. No existing assertion changed.
- **Commit:** 79b355c6d

**3. [Rule 1 - Correctness] RATE-01 and RATE-02 were NOT marked complete in REQUIREMENTS.md**
- **Found during:** the state-update step. The plan's frontmatter carries `requirements: [RATE-01, RATE-02]` and the executor protocol says to run `requirements.mark-complete` on them.
- **Why not:** the requirement text is not satisfied by an unapplied migration. RATE-01 reads "Rate limiting is backed by the project's own Postgres via a SECURITY DEFINER `check_rate_limit` RPC ... `_shared/rate-limit.ts` keeps its exported signature so all five deployed edge functions inherit the change"; RATE-02 reads "The limiter fails CLOSED ... there is no fail-open branch left". Neither is true yet: nothing is applied and `_shared/rate-limit.ts` is untouched. ROADMAP assigns the same two IDs to 66.1-02, 66.1-03 and 66.1-05. Checking them off here would claim a delivered control that does not exist in production -- the exact class of false certification this phase was created to undo. Both remain `Pending` in the traceability table.
- **What was done instead:** `roadmap.update-plan-progress 66.1` ran normally and checked off the 66.1-01 plan line (1 of 5, "In Progress"), which is accurate.

**4. [Rule 3 - Blocking] STATE.md frontmatter hand-corrected after the SDK writes**
- **Found during:** the state-update step, by diffing STATE.md as the recorded `phase.complete` numeric-sort memory requires.
- **Issue:** `state.advance-plan` acted on the STALE position (Phase 66, plan 17 of 17), returned `reason: last_plan`, and stamped `status: verifying` -- false, since Phase 66.1 is mid-flight at 1 of 5. It also deleted `stopped_at`. Separately, `state.record-metric`, `state.add-decision` and `state.record-session` are all no-ops against this STATE.md (it has no Performance Metrics, Decisions or Session section) but each still REWRITES the frontmatter, silently reverting hand edits made before them.
- **Fix:** ran every SDK write first, then hand-corrected `status` back to `executing`, restored an accurate `stopped_at`, updated Current Position to Phase 66.1 plan 1 of 5, and left a comment block in STATE.md recording the ordering hazard so the next executor does not lose the correction the same way. `state.update-progress` derived 56/60 = 47% from disk, which is correct and was kept.
