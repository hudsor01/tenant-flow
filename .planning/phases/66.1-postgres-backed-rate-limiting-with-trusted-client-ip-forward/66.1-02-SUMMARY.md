## THE BLOCKER

The plan fixes the apply mechanism and forbids substituting it: Supabase Management API,
`POST /v1/projects/bshjmbshupiibfiewpxb/database/query`, body built by `jq -Rs` reading the
migration from disk. That path is dead in this environment.

```
$ sbq.sh ping.sql                      # select 1 as ping, current_database(), version()
curl: (22) The requested URL returned error: 401
{"message":"Unauthorized"}

$ curl -o /dev/null -w '%{http_code}' -H @hdr https://api.supabase.com/v1/projects
401                                    # read-only endpoint, same result
```

Retried several minutes apart, same result both times. `SUPABASE_ACCESS_TOKEN` **is** set in the
environment and is well-formed -- 44 characters, `sbp_` prefix, i.e. `sbp_` + 40 hex, the standard
PAT shape. It is simply not accepted.

### The helper was eliminated as the cause, not assumed innocent

A 401 has two candidate causes: a bad credential, or a helper that never transmitted it correctly.
`-H @file` and `--data-binary @file` are exactly the kind of plumbing that fails silently, so the
helper was pointed at a local listener that reports only header *names*, the token *length*, and a
hash of the body -- never a value:

```json
{"has_auth": true, "scheme_ok": true, "token_len": 44,
 "ct": "application/json", "body_bytes": 60, "body_sha_prefix": "9162246e1300"}
```

Expected body bytes: 60. Sent: 60. So the helper transmits a well-formed
`authorization: Bearer <44 chars>`, the correct content type, and a **byte-exact** copy of the file
`jq` read from disk. The mechanism is correct; the credential is rejected. This matches the
project's standing `supabase-cli-functions-deploy-401-pattern` note and the v9.0 residual "db:types
still owner (needs PAT refresh)" -- except that it has now degraded further: that note recorded
`projects list` returning 200 with the same PAT, and it no longer does. The token has been revoked,
rotated or expired since.

## Verification -- all against the APPLIED objects, actual output

**Structure.** table 1, index 1, policies 4, `FOR ALL` policies **0**, RLS on,
`reloptions={fillfactor=70,autovacuum_vacuum_scale_factor=0.02,autovacuum_analyze_scale_factor=0.05,autovacuum_vacuum_cost_delay=0}`,

**Both guards present in the applied `prosrc`** -- `guard1_present=1`, `guard2_present=1`. This is

**Cleanup function**, seeded one already-expired row -> `rows_deleted_by_sweep = 1`. `for update

**Grant lockdown -- and the first attempt was WRONG, which is worth recording.**

| role | sqlstate | verdict |
|---|---|---|
| anon | 42501 | DENIED - insufficient_privilege |
| authenticated | 42501 | DENIED - insufficient_privilege |
| service_role | CALL SUCCEEDED | POSITIVE CONTROL - function exists and is reachable |

ACL reads `{postgres=X/postgres,service_role=X/postgres}`; `has_function_privilege` is true for
service_role, false for anon and authenticated.

The first probe reported 42501 for **all three roles**, including service_role -- which holds
EXECUTE. The positive control is the only reason that was caught. The cause was the probe, not the
grants: it wrote each result to a temp table *while the role was still switched*, so a temp-table
permission error was indistinguishable from a function permission error. Had the control been
omitted, two spurious 42501s would have been recorded as a passing grant lockdown. Rewritten to
capture into variables and write only after `reset role`.

**The two guards, behaviourally.**

| test | detail | verdict |
|---|---|---|
| GUARD 1 -- saturated previous window denies the FIRST request of a new window | `allowed=f`; rows written at current window `0`; weighted_prev `73105` vs limit `10`; elapsed_ratio `0.2689` | PASS |
| GUARD 2 -- setup, 3 admitted against limit 3 | `request_count=3`; last `allowed=t` | PASS |
| GUARD 2 -- 4th request denied AND burns no budget | `allowed=f`; `request_count=3` unchanged; `remaining=0` | PASS |

GUARD 1's case is the one a one-guard implementation gets wrong: no row exists for the current
window, so the INSERT path is taken and `ON CONFLICT DO UPDATE ... WHERE` is never evaluated. Only
GUARD 1 can deny it, and it did -- with zero rows written.

**Test writes cleaned.** `delete ... where bucket_key like 'verify:66.1-02:%' or in (...)` ->
`total_rows_remaining = 0`, `probe_rows_remaining = 0`. The table is empty. Transaction semantics
were not relied on; the explicit prefixed delete plus zero-count readback ran, as the plan
anticipated.
