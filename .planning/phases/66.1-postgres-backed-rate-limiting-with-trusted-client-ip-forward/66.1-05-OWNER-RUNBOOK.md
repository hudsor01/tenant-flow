## Steps

### 1. Rotate the PAT

Generate at <https://supabase.com/dashboard/account/tokens>, then in the shell you will run the
deploy from:

```
export SUPABASE_ACCESS_TOKEN='<new token>'
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  https://api.supabase.com/v1/projects        # expect 200
```

### 2. Purge the cached copy of the old token

```
rm -rf .next
```

The revoked PAT sits in plaintext in four `.next/dev/cache/turbopack/*.sst` files. `.next/` is
git-ignored with zero tracked files so it never reached the repo, and the token is already dead --
but clear it rather than leave a credential-shaped artifact on disk.

### 3. Generate and set the forwarding secret

Generate it yourself; never paste it into this chat.

```
openssl rand -hex 32
```

Set the SAME value in BOTH places, named `CLIENT_IP_FORWARD_SECRET`:

- Supabase -> Project Settings -> Edge Functions -> Secrets
- Vercel -> Project -> Settings -> Environment Variables (Production). **Server-side only.** Do not
  prefix it `NEXT_PUBLIC_` -- that would ship it to every browser and hand any visitor the ability
  to forge their own rate-limit identity. Two source gates in `src/app/apply/[token]/__tests__/apply-context.test.ts` now enforce this -- they were claimed here before they existed, which is why this sentence is worth reading twice: the protection is real as of the cycle-6 fix, not before it.

**Order does not matter, and this is verified by execution, not assumed.** Plan 04's trust matrix
walks all four provisioning orders; every partial state falls back to the connection address, which
is today's exact behaviour. You cannot create a window where things get worse.

**Do not set it to an empty string.** Two empty secrets compare equal, which would trust forged
headers -- a total bypass caused by *omission*. Plan 04 ships an explicit guard against this and a
test for it, but do not lean on it.

### 4. Set `SENTRY_DSN` as a Supabase function secret

Same Edge Functions -> Secrets screen. Without it the bind is a deliberate silent no-op, so error
reporting stays dark for all 17 functions that use `errorResponse()`.

### 5. Deploy the five functions

```
bun scripts/deploy-edge-functions.ts
```

Reads from disk, so nothing passes through a model. Expect these versions to increment:
`apply-token` 5, `sign-lease-token` 7, `lease-signature` 12, `newsletter-subscribe` 21,
`send-contact-email` 4.

### 6. Tell me, and I will run the live proofs

With the deploy done I can verify over MCP and HTTP:

- the limiter actually enforces end-to-end against the deployed function
- an unset/invalid/forged forwarding header does not change the rate-limit identity
- `x-vercel-forwarded-for` is genuinely populated for an RSC render -- **the hard gate**; if it is
  absent the mechanism silently falls back to the shared egress bucket and the phase's headline fix
  does nothing
- Sentry actually receives an event, including from a non-rate-limit function
- latency returns to the ~0.28s order, from the measured 9.0-9.2s two-limiter baseline
- the `apply-context-client` 60/60s bucket limits per client rather than product-wide

### 7. Sentry alert rule -- console only

Create an issue alert on the `rate_limit_error` tag. No CI check can verify this exists; the only
real evidence is watching it fire once. Note plan 05 had to add a `tags` argument for this: the
limiter emitted `event` as Sentry `extra`, which is not indexable, so an alert condition could
never have matched it.

## Two things that stay unproven until you act

- **The 64-client concurrency proof has never run.** It needs the RLS integration credentials in
  `.env.local` (Supabase URL, service-role key, publishable key, ownerA login). This is the phase's
  headline evidence. The two guards are proven sequentially against production, but research
  measured a naive limiter admitting 156/159/161 against a limit of 100 under 64 clients while
  scoring exactly 100 single-threaded -- so a sequential pass is precisely the evidence that cannot
  tell a correct limiter from a broken one.
- **Neither headline proof has an automated runner.** No CI job runs `deno test`, and the RLS suite
  is owner-run against production. Recorded, not silently absorbed.
