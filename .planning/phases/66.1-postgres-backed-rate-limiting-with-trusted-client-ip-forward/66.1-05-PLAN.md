**READ THIS BEFORE TASK 1. This plan changes what five live public endpoints do.**

Every prior plan in this phase was inert in production. 66.1-02 added database objects nothing
calls. 66.1-03 and 66.1-04 edited source that has never been deployed. This plan is the moment the
work becomes real, and it is the only plan in the phase whose failure is visible to a stranger.

**What changes, precisely:**

| Function | Live version now | What changes |
|---|---|---|
| `apply-token` | 5 | Rental application intake. Limiter moves to Postgres and FAILS CLOSED. Gains a trust-gated per-client context bucket. |
| `sign-lease-token` | 7 | Tenant e-sign link resolution. Limiter moves to Postgres and fails closed. |
| `lease-signature` | 12 | E-sign submission + metering. Same. |
| `newsletter-subscribe` | 21 | Public marketing form. Same. |
| `send-contact-email` | 4 | Public contact form. Same. |

**The behavioural change in one sentence:** today these five surfaces have NO working rate limits
at all (the Upstash database was reaped months ago and the limiter fails open, silently); after this
deploy they have real limits, and if the database is unreachable they return 429 instead of serving.

**Blast radius.** All five are `verify_jwt = false` public endpoints. Two of them
(`apply-token`, `sign-lease-token`) sit on revenue-adjacent flows: a prospective tenant filling in a
rental application, and a tenant signing a lease. A bad deploy here is a stranger being unable to
apply for a home or sign a lease, with no error they can act on. That is the cost side. The benefit
side is that the product's only public unauthenticated write surface currently has no abuse control
whatsoever.

**Rollback: redeploy the previous source. How the previous source is obtained -- two paths, both
captured in Task 1 BEFORE anything is deployed:**

1. **The reviewed source (authoritative for a redeploy).** `git merge-base HEAD origin/main` is the
   commit before this phase touched `supabase/functions/`. `git worktree add $SCRATCH/pre-phase
   <sha>` materialises that tree, and `bun scripts/deploy-edge-functions.ts <five slugs>` run from
   inside it re-uploads exactly the source that is live today. This is the path to use, because the
   deploy script walks relative imports from each entrypoint and ships `_shared/*` plus `deno.json`
   in the layout the platform expects.
2. **The deployed bytes (authoritative for diagnosis).** `mcp__supabase__get_edge_function` returns
   the file set the platform is actually serving. Captured to `$SCRATCH/rollback/<slug>/` as the
   record of what was live, and as the comparison target if path 1 ever disagrees with reality.

Rollback takes minutes and needs no owner decision beyond starting it. Supabase keeps the old
versions, so a rollback is a forward deploy of old source, not a deletion of anything.

**What is reversible, what is not:**

- **Reversible in minutes:** the five function deploys (redeploy per above); the two secrets (unset
  them); the Sentry alert rule (delete it); the `apply-context-client` bucket (it is gated on the
  secret, so unsetting the secret disables it).
- **Reversible, but do NOT:** 66.1-02's migration rollback. Dropping `check_rate_limit` after this
  deploy yields `PGRST202` from a fail-closed limiter, i.e. a hard 429 on all five surfaces. That
  script's own header says so. It is safe only while the functions are on pre-phase source.
- **NOT reversible:** requests that real users make during the windows this plan deliberately opens.
  There are two. (a) The seconds between a bad deploy and its rollback. (b) The deliberate
  revoke/grant fail-closed probe in Task 6, during which all five surfaces deny. That probe is two
  SQL statements run back to back with the grant in an `EXIT` trap; it is bounded by seconds, and it
  is the only way to prove RATE-02 and RATE-04 together in production. Run it at a low-traffic hour.
- **NOT reversible by this plan, and not attempted:** nothing in the database. This plan issues no
  DDL except the deliberate revoke and its immediate re-grant.

**The ordering is deliberate and load-bearing.** The functions are deployed BEFORE
`CLIENT_IP_FORWARD_SECRET` is set. That is not laziness -- it is the only window in which the
highest-severity property in the phase can be tested in production. See
`<the_unset_secret_window_is_the_point>` below. 66.1-04 walked all four provisioning orders and
found none that produces a window of changed behaviour, so the ordering costs nothing and buys the
proof.

Task 3 is the blocking owner gate. Nothing is uploaded before it clears.

<the_unset_secret_window_is_the_point>
**This is the highest-severity item in the phase and the reason the task order looks unusual.**

66.1-04 found it: if `configuredSecret` and `presentedSecret` are both `""`, a constant-time
compare returns TRUE. An unconfigured secret would therefore trust any caller who sends two empty
headers -- a **total bypass produced by failing to configure something**, which is the exact
inversion of how a security control is supposed to degrade. It is invisible to every other row of
the trust matrix, and it is available to anyone who reads the source.

04 guarded it on both sides independently: `trustedClientIpHeaders` refuses to forward when the
secret is empty after `.trim()`, and `decideForwardedClientIp` checks `configuredSecret`
non-emptiness **before any comparison runs**. Both, because either alone makes the property depend
on deployment state.

**Task 1 verifies those guards shipped. Task 5 proves it in production.** Supabase function secrets
are project-wide, so there is no function without the secret once it is set -- which means the
window between "functions deployed" and "secret configured" is the ONLY moment this can ever be
tested against a real isolate. Miss it and the assertion is a unit test forever.

**The four provisioning orders, carried from 04's Task 3(e) so this plan does not re-derive them:**

| Vercel | Supabase | Result | Behaviour |
|---|---|---|---|
| set | unset | `no_configured_secret` | identical to today |
| unset | set | `no_presented_secret` | identical to today |
| both, mismatched | | `secret_mismatch` | identical to today |
| neither | | `no_configured_secret` | identical to today, gated bucket never entered |

The structural reason there is no bad order: trust is granted at exactly one `return` requiring all
five conditions, so any missing piece is a fallback rather than a partial state. **Rotation is
therefore safe in any order too** -- the worst outcome of a mismatched window is the status quo,
never a wrong-identity grant.
</the_unset_secret_window_is_the_point>

<the_alert_rule_cannot_match_an_extra>
**A correction this plan must make before deploying, or RATE-04 ships as decoration.**

66.1-03 emits the outage event as `captureWebhookError(err, { event: "rate_limit_error", ... })`,
and `captureWebhookError` forwards its second argument to `Sentry.captureException` as **`extra`**.

Sentry `extra` is attached to the event body but is **not indexed**. Sentry issue-alert conditions
match on `message`, on `exception.type` / `exception.value`, on `level`, and on **tags** -- not on
extras. So the rule the outline describes ("alert on `event: rate_limit_error`") cannot be built
against an extra, and matching on `message` instead would silently miss every real case: when the
database is unreachable the captured error is a transport error whose message is something like
"fetch failed", carrying no trace of `rate_limit_error` at all.

**Fix, in Task 1, before the deploy:** give `captureWebhookError` an optional third parameter
`tags: Record<string, string>` forwarded to `Sentry.captureException`'s `tags`, and have
`rate-limit.ts` pass `{ event: "rate_limit_error", error_class: <the class> }`. Additive: no existing
call site changes, and both existing call shapes keep working. `error_class` has exactly seven
possible values, so tag cardinality stays trivial.

**Never tag the bucket key.** Tags are indexed and searchable, so tagging the key would build a
searchable index of client IP addresses inside Sentry -- strictly worse than the extra it replaced.
T-66.1-34.

**This is a deliberate deviation from the outline's file map**, which gives this plan only
`deferred-items.md`. Flagged rather than smuggled: RATE-04 is this plan's requirement, the alert is
this plan's deliverable, and an alert that cannot match its own event is the failure mode this
entire phase exists to eliminate. The edit is ~3 lines in `errors.ts` and ~1 in `rate-limit.ts`, it
lands pre-deploy so the deployed source emits the tag, and Task 6 proves the rule fires rather than
trusting this reasoning.

**Honest statement of what CI can check, since the requirement invites overclaiming:** the alert
rule is Sentry-side configuration. It cannot be committed, cannot be reviewed in a diff, and **no
CI check in this repo can verify it exists**. Nothing stops someone deleting it. Its only durable
protections are (a) 66.1-03's source assertion that the `rate_limit_error` literal survives in
`rate-limit.ts`, (b) this plan's extension of that assertion to the tag, and (c) Task 6 having
watched it fire once. Do not write anything in the SUMMARY that implies more than that.
</the_alert_rule_cannot_match_an_extra>
