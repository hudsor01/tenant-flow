## The Sentry bind -- what proves it, and what does not

`Sentry.captureException` returns an event id whether or not a client is bound. That is the whole reason this defect survived: every assertion of the form "the capture happened" passes identically before and after. So acceptance is client-BOUNDNESS.

**Proven here, by executed Vitest (structural, over `errors.ts` source):**
- `Sentry.init(` is present and `getClient()` guards it.
- All four exports -- `errorResponse`, `captureWebhookError`, `captureWebhookWarning`, `logEvent` -- call `ensureSentryClient()` at an index strictly before their first `Sentry.<method>(` call, compared **within each function's balanced-brace slice**, not file-wide. An init wired into only one of four entry points would make monitoring depend on which path fires first in a given isolate.
- The DSN is read via `Deno.env.get("SENTRY_DSN")` and `validateEnv` appears nowhere in the file.

**Written but NOT EXECUTED:** `supabase/functions/tests/rate-limit-sentry-test.ts` asserts `Sentry.getClient()` is `undefined` after a capture with no DSN, and defined with `getOptions().dsn` matching after a capture with one. The unset case runs FIRST on purpose -- the SDK keeps the client on a process-global carrier, so reordering makes the first case vacuous. The file carries no conditional guard of any kind.

**Envelope-level proof (`client.on("beforeEnvelope", ...)`) was not attempted.** With no runtime available to validate it, shipping a hook-based assertion that has never run would be worse than not shipping it. It belongs to 66.1-05, with `SENTRY_DSN` set as a Supabase function secret as its precondition.

**NOT proven anywhere in this plan:** that an event reaches Sentry's servers. That needs a real DSN, egress from a deployed isolate, and a look at the Sentry project.
