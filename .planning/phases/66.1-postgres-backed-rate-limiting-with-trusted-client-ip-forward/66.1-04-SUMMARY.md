## The header choice, and what it supersedes

Read from Vercel's request-headers documentation (`vercel.com/docs/headers/request-headers`, last updated 2025-12-13), not inferred:

- **`x-forwarded-for`** — "The public IP address of the client... we currently **overwrite** the X-Forwarded-For header and **do not forward external IPs**. This restriction is in place **to prevent IP spoofing**." Only Enterprise customers with a purchased Trusted Proxy permission can have a custom value honoured.
- **`x-vercel-forwarded-for`** — "identical to the x-forwarded-for header. **However, x-forwarded-for could be overwritten if you're using a proxy on top of Vercel.**"
- **`x-real-ip`** — "identical to the x-forwarded-for header."

**Chosen:** `x-vercel-forwarded-for`, falling back to `x-forwarded-for`. Strictly the more attested of the two, at the cost of one extra lookup; the fallback exists because the docs do not guarantee the Vercel-specific header on every runtime.

**Rejected:** `x-real-ip` (adds zero attestation over a header already read — a coin flip dressed as a decision), and any convenience accessor (`@vercel/functions`' `ipAddress()`, framework helpers) because the precedence must be reviewable in the diff rather than resolved inside a dependency.

**THIS SUPERSEDES THE OUTLINE.** `66.1-PLAN-OUTLINE.md`'s per-plan note for 66.1-04 instructs "at Vercel take the **FIRST** segment". Its underlying claim — that Vercel overwrites XFF to prevent spoofing — is confirmed correct by the citation above, but the instruction built on it is not what shipped. Vercel documents each of these as carrying **the** client address, singular, so a multi-segment value is **refused, not parsed**, on both sides. Both directions of the wrong guess are eliminated by not guessing, and the failure mode is today's behaviour.

**Still unproven and owned by 66.1-05:** that production actually populates `x-vercel-forwarded-for` for an RSC render.

| 3 | secret on the caller, absent on the function | `trusted: false`, `no_configured_secret` -> connection address |

Plus three closure assertions: trust is granted **iff** (non-empty configured secret AND presented === configured AND the address normalizes), stated over the whole input set rather than as a count; every declared reject reason is reachable and none is produced that is not declared; and a trusted decision always carries an address while an untrusted one never does.

**Row 7 is the highest-severity item in the phase and it is not in the obvious six.** Two empty strings are equal to any comparator, so without the emptiness check running *before* the compare, failing to configure the secret would make the system **more permissive than configuring it** — a total bypass by omission, available to anyone sending two empty headers, and invisible to every other row. `send-lease-reminders` escapes this only because `REMINDERS_INVOKE_SECRET` sits in `validateEnv({ required })` and the isolate dies first; D-05 makes this secret optional by design, so it cannot inherit that protection. Guarded independently on **both** sides, because either one being the only guard makes the property depend on deployment state.

## The four provisioning orders — walked by execution, not restated

Run against the real `decideForwardedClientIp` + `timingSafeEqualStr`:

```
Vercel set, Supabase unset                     -> trusted=false reason=no_configured_secret clientIp=-
Supabase set, Vercel unset                     -> trusted=false reason=no_presented_secret  clientIp=-
both set but DIFFERENT (typo / mid-rotation)   -> trusted=false reason=secret_mismatch      clientIp=-
neither set                                    -> trusted=false reason=no_configured_secret clientIp=-
[control] both set and equal                   -> trusted=true  reason=-                    clientIp=203.0.113.9
```

Every ordering falls back to the connection address — today's exact behaviour. The control proves the walk is not vacuous. **Rotation is therefore safe in any order:** the worst outcome of a mismatched window is the status quo, never a wrong-identity grant. The reason is structural, not incidental: trust is granted at exactly one `return` requiring all five conditions, so any missing piece is a fallback rather than a partial state. **66.1-05 may provision in whichever order is convenient.**

## The 3,000/min ceiling decision

**Kept at 3,000/60s on `prefix: "apply-context"`, keyed on `tokenHash`. Justification rewritten. A separate trust-gated per-client bucket added beside it.**

- **Why the number stays.** It is a per-listing *aggregate capacity ceiling*. A per-client bucket does not replace it: a thousand distinct clients each staying under their own limit still sum to a thousand times the load, and this is the only thing that bounds the sum. It also still applies to every untrusted request, which is all of them until 66.1-05.
- **What was obsolete and is now gone.** `apply-token/index.ts`'s "WHERE THE REAL PER-CLIENT LIMIT BELONGS: `src/proxy.ts` ... recorded in deferred-items.md" block, and the contract test's "no key it can compute separates them". Both were true *of the input this function had*, not of the function. RATE-03 changes the input, so the general result no longer holds; `src/proxy.ts` / a WAF is now a **complement**, not the only possible home. Leaving those in place would have had the next reviewer conclude per-client limiting was still impossible with the mechanism sitting three lines above.
- **What was added.** `prefix: "apply-context-client"`, 60/60s, `identifier: trustedIp`, entered only when `getTrustedClientIp` returns non-null, **before** the ceiling (the more precise control reports first). The prefix is deliberately NOT `apply-context-ip`, so the pre-existing `not.toContain('prefix: "apply-context-ip"')` guard stays intact and still passes.
- **Why 60/min.** One context call per page load. A human reloading faster than once a second for a minute is not a human; carrier-NAT and corporate-egress clients sit far below it on one niche listing. It is per *verified* client, so crawlers and link-preview bots each land in their own bucket.
- **Cost.** When trusted, two limiter RPCs instead of one, ~10-30ms each same-region — on a path that measured 9.0-9.2s on 2026-08-09.
- **What would change this.** Production evidence that one listing legitimately exceeds 3,000 context calls/min (raise the ceiling), or that verified per-client traffic routinely approaches 60/min (raise that). 66.1-05's live check is the first chance to see real numbers.
