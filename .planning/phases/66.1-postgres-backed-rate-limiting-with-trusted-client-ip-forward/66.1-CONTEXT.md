# Phase 66.1 Context — Postgres-backed rate limiting + trusted client-IP forwarding

## How this phase came to exist

Phase 66's review found that **every rate limit in the product was a no-op, and had been for
months**. Measured against the deployed function on 2026-08-09: an action with zero limiter calls
returned in 0.28s; the context action with two took 9.0–9.2s. The same edge-function logs showed
`sign-lease-token` at 9.4–9.6s — a function that predates Phase 66 entirely. Full latency cost,
zero enforcement, project-wide.

Root cause, in two layers:

1. **Upstash's free-tier database was reaped for inactivity.** The tier allows only ONE database
   per account and the owner's single slot already serves another purpose, so the dependency
   cannot simply be restored.
2. **The limiter lives in a different failure domain from the writes it guards.** That is why it
   was written to fail open, and why the outage was silent — there was no path in which anything
   noticed.

The second layer is the real defect. Any replacement that is also a separate service inherits it.

## Decisions (owner-approved in session, not planner-inferred)

- **D-01 — Postgres, not another service.** `check_rate_limit` becomes a SECURITY DEFINER RPC in
  the project's own database. This is not a vendor swap: it puts the limiter in the SAME failure
  domain as the write it guards.
- **D-02 — Fails CLOSED, and there is no fail-open branch left.** Because the limiter and the
  write now share a domain, an unreachable database fails the write anyway. Delete the fail-open
  `catch` rather than porting it — a fail-open branch is exactly where the last outage hid.
- **D-03 — `_shared/rate-limit.ts` keeps its exported signature.** All five deployed edge
  functions (`apply-token`, `sign-lease-token`, `lease-signature`, `newsletter-subscribe`,
  `send-contact-email`) then inherit the change with no call-site edits.
- **D-04 — D5 is closed by fixing the BOUNDARY, not the key.** The `context` action is called
  only server-side by the RSC, so `getClientIp` returns the Vercel egress for 100% of genuine
  traffic. **Two previous attempts to fix this inside the edge function both failed** (see
  "Rejected alternatives"). The RSC forwards the true client address, authenticated by a
  constant-time shared-secret Bearer.
- **D-05 — The forwarding path is non-regressive BY CONSTRUCTION.** Absent secret, invalid
  secret, or missing header falls back to the connection address — today's exact behaviour. The
  change can never be worse than the status quo.
- **D-06 — Reuse the established secret pattern.** `supabase/functions/send-lease-reminders/index.ts:208`
  already does a constant-time shared-secret Bearer compare (`REMINDERS_INVOKE_SECRET`, mirrored
  into `app_config`). Follow it; do not invent a second mechanism.
- **D-07 — Delete the 800ms timeout.** It exists only to bound a hanging Upstash round trip. A
  same-region Postgres call is ~10–30ms.
- **D-08 — The outage must be observable.** `rateLimit()` already emits a structured
  `rate_limit_error`. Wire a Sentry alert on it. **Without this the phase merely resets the clock
  on the same silent failure** — that is the point of RATE-04, not a nice-to-have.
- **D-09 — The new trust boundary goes in the threat model.** If the forwarding secret leaks, an
  attacker can spoof their rate-limit identity. Same handling as `REMINDERS_INVOKE_SECRET`:
  Supabase function secret + Vercel env var, never in the repo.
- **D-10 — One atomic statement, no read-then-write.** `INSERT … ON CONFLICT DO UPDATE`, matching
  the discipline `submit_rental_application` already uses. A check-then-act limiter is invisible
  to any single-threaded test — Phase 66 has a worked example of exactly that class.

## Rejected alternatives (and why — do not re-litigate)

- **Share the existing Upstash database via key prefix.** Free and zero code, but re-buys the
  exact failure just discovered: separate failure domain, same idle-reaping, and now two
  applications coupled to one free database.
- **A second Upstash account/database.** Free tier permits one per account; a second account to
  dodge that is a licensing dodge, not an architecture.
- **Fix D5 with a smarter key inside the edge function.** Attempted TWICE and wrong both times.
  v1 keyed on the token alone — a public kill switch, since D-03a publishes the token to listing
  sites. v2 keyed on `${tokenHash}:${getClientIp(req)}` — defeated by simply GETting the public
  page, which lands the attacker in the same egress-keyed bucket real applicants share. **General
  result: at that function an attacker and an applicant are indistinguishable. No key it can
  compute separates them.** Both attempts shipped a passing test that certified a property the
  code did not have.
- **Rate limit in Next.js middleware for all routes.** Adds a database round trip to every request
  on every route to solve a problem on one public surface.
- **Drop the edge limiter entirely.** Legitimate, and the DB per-link cap under the token row's
  `FOR UPDATE` lock would remain the fail-closed bound — but it loses the 5/hour submit cap, which
  is a genuine control on the product's only public unauthenticated write surface.
- **Vercel Firewall / WAF.** Genuinely good, and it sees the real client IP before the app runs.
  Not chosen because it is plan-dependent config outside the repo, unversioned and unreviewable in
  CI. Worth revisiting as a complement, not as the mechanism.

## Current state of the surface being protected

- The `apply-token` context bucket was already re-scoped to an honest **per-listing capacity
  ceiling** (3,000/min, keyed on `tokenHash` alone) because no per-caller key was achievable
  there. The address-only 300/min ceiling was REMOVED — keyed on the shared egress it was a
  product-wide cap needing no token at all.
- Once RATE-03 lands and a real per-client key exists, that ceiling should be revisited: it is
  currently sized for "cannot distinguish callers", which will no longer be true.
- `apply-token` is at **v5**; `sign-lease-token` v7, `lease-signature` v12,
  `newsletter-subscribe` v21, `send-contact-email` v4.
