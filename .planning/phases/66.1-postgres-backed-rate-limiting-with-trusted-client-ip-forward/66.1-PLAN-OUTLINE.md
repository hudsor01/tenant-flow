## Per-plan notes

### 66.1-01 — Migration + the concurrency proof
Transcribe the research SQL verbatim: table with `fillfactor = 70`, no index on `request_count`,
autovacuum overrides, four per-operation service_role RLS policies, `revoke ... from public, anon,
authenticated`; then `check_rate_limit(text, integer, integer)` with `security definer`,
`search_path = public`, `lock_timeout = '250ms'`, the unlocked previous-window read, **GUARD 1** on
the `INSERT ... SELECT ... WHERE v_prev_weighted < p_max_requests` and **GUARD 2** on the
`DO UPDATE ... WHERE`; then `cleanup_rate_limit_counters()` (bounded 10k batches, `FOR UPDATE SKIP
LOCKED`, 50-iteration cap, **no archive table** — state that deviation in the migration header) and
`cron.schedule('cleanup-rate-limit-counters', '25 3 * * *', ...)` guarded by an `unschedule`.
`p_window_ms` is `integer`, not `bigint` — a `bigint` parameter breaks plain-SQL function
resolution and every psql/RLS test would need `::bigint`.

This plan owns the limiter statement, so **it owns the concurrent test** (trap 1): 64 parallel
clients via `Promise.all`, 2,560 attempts, limit 100, assert exactly 100 admitted across 3 runs — a
sequential loop admits exactly 100 against a *broken* check-then-act limiter, which is how Phase 66
shipped two passing tests for properties the code did not have. Include the ~15-line naive control
so the test can be proven non-vacuous. Also assert: saturated previous window denies at a new
boundary AND writes zero rows (GUARD 1), denied requests do not increment, and `anon` cannot
execute the RPC.

### 66.1-03 — The limiter rewrite (RATE-01/02/04)
Swap Upstash for `supabase.rpc('check_rate_limit', ...)` through a module-scope cached
service-role client built from the platform-injected `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`
(comment why CLAUDE.md's no-module-level-client rule targets the frontend hook layer and inverts
here). Keep both exported signatures exactly (`getClientIp`, `rateLimit`) so all **11** call sites
across five functions inherit it untouched — CONTEXT says `lease-signature` has 2, it has 3
(lines 203, 385, 590); the `lease-esign-finalize` site must not be missed. Delete the 800ms
timeout and both `deno.json` import-map entries; add no new timeout (pitfall 8).

**Keep the `catch`, change its return from `null` to a denial.** Deleting it outright scatters
throws into five different handlers. Every row of the research's 8-class taxonomy denies and emits
`rate_limit_error`: transport failure, PostgREST 5xx, `55P03`, `57014`, missing env, `PGRST202`,
and empty/malformed payload. Use `.single()` or an explicit shape check — `returns table` arrives
as an array and `result?.allowed === false` on `undefined` **admits**. Return **429** with
`Retry-After` when the database is unreachable, not 503 (`application-outcome.tsx:34` reasons about
the submit limiter's hour window; verify before locking). Add a source-grep contract test asserting
no `return null` survives in a catch, per the `apply-token-contract.test.ts` precedent. Update
`supabase/functions/tests/lease-signature-metering-test.ts:26`, whose comment asserts the now-dead
fail-open premise — update it, never skip it.

**RATE-04 mechanism — decided: real Sentry init, not log-based alerting.** Verified this session:
`Sentry.init()` runs in `stripe-webhooks/index.ts` **only**, so `_shared/errors.ts`'s
`captureException` is a no-op in all five in-scope functions and RATE-04 as written in REQUIREMENTS
is not satisfiable today. The console.error alternative was rejected because D-08 and the
requirement both say "reaches Sentry", and because Supabase log-based alerting is out-of-repo,
unversioned plan-tier config — the same disqualifier that rejected the WAF. Add
`supabase/functions/_shared/sentry.ts`: init once per isolate, guarded on `SENTRY_DSN` presence,
called from `rate-limit.ts`. **The criterion must assert the mechanism fires**, not that a call
exists: a unit test spies the Sentry capture and asserts a `rate_limit_error` event is transmitted
with a DSN configured, and 66.1-05 proves it end-to-end in production.

### 66.1-04 — Trusted client-IP forwarding, both sides together (RATE-03)
**Trap 2 is why this is one plan.** `x-forwarded-for` has opposite correct answers in the two files
this plan touches: at Vercel take the **FIRST** segment (Vercel overwrites the header specifically
to prevent spoofing), at the Supabase edge take the **LAST** (attacker-supplied, gateway appends).
Both edits carry a comment naming the other file and why they differ, and the unit tests assert
both directions — otherwise a later reviewer "fixes" one to match the other.

RSC side: `src/app/apply/[token]/apply-context.ts` reads `headers()` from `next/headers` (async
since Next 15; the repo already imports `cookies` from that module) and sends two dedicated
headers — `x-tf-client-ip` and `x-tf-forward-secret`. Do **not** overload `Authorization`;
`lease-signature` already extracts user JWTs from it. Edge side: `getClientIp` gains a branch
**in front of** today's logic that trusts the forwarded value only when `timingSafeEqualStr`
(existing `_shared/timing-safe.ts`) validates the secret, then normalizes it — first comma segment,
≤45 chars, `[0-9a-fA-F:.]` only — before it becomes a database key. Every failure path (absent
header, absent secret, wrong secret, malformed address) falls through to today's exact code, which
is what makes D-05's non-regression structural rather than tested.

Two comments are load-bearing and both look like oversights to a reviewer: `cors.ts` must state
that the forwarding headers are deliberately absent from `Access-Control-Allow-Headers` (adding
them would make the spoofing header browser-sendable, defeating the whole control), and
`timing-safe.ts:5-6` must be corrected — Deno does not expose `crypto.subtle.timingSafeEqual`, so
the XOR fallback is the live path, not the fallback. The `cf-connecting-ip`-first hedge can become
an assertion: `OPTIONS` on the function returns `cf-ray` / `server: cloudflare`, so Cloudflare
overwrites any inbound copy. `apply-context` ceiling re-tuning is explicitly **out of scope**.

### 66.1-05 — OWNER-GATED go-live
`autonomous: false`, and it is the last wave, so nothing downstream depends on it. Owner steps:
(a) set `CLIENT_IP_FORWARD_SECRET` to the same value in **both** places — Supabase function secret
and Vercel env var, never in the repo (D-09 threat boundary: a leak buys a spoofed rate-limit
identity, rotatable independently); (b) confirm/set `SENTRY_DSN` as a Supabase function secret;
(c) redeploy all five functions with `bun scripts/deploy-edge-functions.ts` — **slug list verified
present** at `scripts/deploy-edge-functions.ts:32-44`: `apply-token`, `lease-signature`,
`newsletter-subscribe`, `send-contact-email`, `sign-lease-token`; the Supabase CLI 401s, so this
script is the path; (d) create the Sentry alert rule on `rate_limit_error` (Sentry-side config,
cannot be committed).

Live acceptance, bounded and reversible, proving RATE-02 and RATE-04 together in production:
`revoke execute on function public.check_rate_limit(text,integer,integer) from service_role;` →
hit `newsletter-subscribe` once → assert **429** and a new Sentry issue carrying
`event: "rate_limit_error"` → `grant execute ... to service_role;` immediately. Run the two
statements back to back; all five guarded surfaces deny for the seconds in between. Then confirm
RATE-03 on a real `/apply/[token]` view (bucket key is the applicant address, not the Vercel
egress), check `select n_tup_upd, n_tup_hot_upd from pg_stat_user_tables where relname =
'rate_limit_counters'` is >95% HOT, unset the dead `UPSTASH_REDIS_REST_URL` /
`UPSTASH_REDIS_REST_TOKEN` secrets, and record in
`.planning/phases/66-rental-application-intake/deferred-items.md` that D5 is closed by fixing the
boundary rather than the key.
