<checkpoint_this_plan_writes_to_production>

**READ THIS BEFORE TASK 1. This plan modifies the production database.**

Project ref `bshjmbshupiibfiewpxb`, region us-east-2. There is no staging environment in this
project; `tests/integration/rls/` has always run against production, and this apply follows the
same path.

**What it creates -- four objects, all new:**

| Object | Kind |
|---|---|
| `public.rate_limit_counters` | table (+ 1 index on `expires_at`, + 4 per-operation service_role RLS policies) |
| `public.check_rate_limit(text, integer, integer)` | SECURITY DEFINER function |
| `public.cleanup_rate_limit_counters()` | SECURITY DEFINER function |
| `cleanup-rate-limit-counters` | pg_cron job at `25 3 * * *` |

**It is additive only.** No existing table, function, policy, grant, trigger or cron job is
altered or dropped. The migration contains no `alter`, no `drop` of any pre-existing object, and
no `update` against application data. The only `unschedule` in the file is the idempotency guard
for the job this migration itself creates. Task 1 proves this by static inspection before anything
is sent, so the claim is checked rather than asserted.

**Nothing consumes these objects yet.** The five deployed edge functions still carry the Upstash
module; the RPC rewrite is 66.1-03 and go-live is 66.1-05. Applying this migration changes the
behaviour of zero live code paths. It is a schema addition sitting idle until a later wave wires
it up -- which is exactly why it is safe to apply now and verify at leisure.

**Rollback, in this order** (Task 1 writes it to disk as an executable file, before the apply):

1. `select cron.unschedule('cleanup-rate-limit-counters') where exists (...);`
2. `drop function if exists public.cleanup_rate_limit_counters();`
3. `drop function if exists public.check_rate_limit(text, integer, integer);`
4. `drop table if exists public.rate_limit_counters;`
5. `delete from supabase_migrations.schema_migrations where version = '<applied version>';`

Order is load-bearing: unscheduling after dropping the function leaves a cron entry that errors
every night at 3:25 UTC. Dropping the table takes its index and its four policies with it.
Rollback is total -- afterwards the database is byte-for-byte in its pre-apply state, because
nothing else references any of these names.

**Blast radius if this goes wrong:** confined to the four new objects. The realistic failure is a
partial apply (some objects created, others not), which Task 3 detects with a five-way object
count and Task 1's rollback script clears in one call.

Task 2 is the blocking owner gate. Do not send anything to the Management API before it clears.

<the_apply_mechanism_is_settled_do_not_substitute>

Apply via the **Supabase Management API**, `POST https://api.supabase.com/v1/projects/bshjmbshupiibfiewpxb/database/query`,
with the request body built by `jq -Rs '{query: .}'` **reading the migration file from disk**.

Do **not** use `mcp__supabase__apply_migration`. Two independent reasons, both of which have
burned this project:

1. **Fidelity.** `apply_migration` takes the SQL as a tool argument, which means the bytes that
   reach Postgres are bytes the model re-emitted. The `edge-deploy-mcp-fidelity` incident is the
   recorded precedent: MCP-mediated source transfer corrupted non-ASCII content, and the corruption
   was only detectable by reading the artifact back afterwards. `jq -Rs` reading the file handle
   means the bytes applied are the bytes 66.1-01 authored and a reviewer read. 66.1-01 made the
   file pure ASCII specifically to shrink this risk; do not spend the margin it bought.
2. **Version drift.** `apply_migration` assigns its own prod-side timestamp, which is why this
   project has a standing `migration-mcp-prod-drift` rule requiring a filename reconcile after
   every MCP apply. The Management API path lets us hand-insert the `schema_migrations` row with
   the version we choose, so the repo filename and the prod version can match by construction.

Reason 2 is a property of the path, not a guarantee. **Verify it anyway** with
`mcp__supabase__list_migrations` (read-only, so the fidelity objection does not apply) and rename
the repo file if the versions differ. Belt and braces.

**Credential handling is part of the mechanism.** The token lives in `SUPABASE_ACCESS_TOKEN` in
the environment. It is never echoed, never interpolated into a message, never written into any
file under the repo, never placed in a command's argv (where `ps` exposes it), and never included
in the SUMMARY. `set -x` is forbidden in every script this plan writes.

</the_apply_mechanism_is_settled_do_not_substitute>

<why_the_verification_looks_like_this>

"The Management API returned 201" proves the SQL parsed. Nothing more. It does not prove the
limiter limits, that the guards guard, or that `anon` cannot call the function.

Phase 66's review found **seven** distinct green-but-proves-nothing mechanisms in this codebase --
tests that certified properties the code did not have. A prod-apply plan whose gate is an HTTP
status code would be the eighth, and it would be the worst of the set, because everything in waves
3 through 5 is built on the belief that this object works.

So every acceptance criterion below is a **behaviour observed against production**, and each one
names the broken state it catches. Structural reads that cannot distinguish a working object from
a broken one -- `pg_proc.proacl` for grants, "the function exists" for the guards -- are explicitly
rejected as gates and may appear only as corroboration.

</why_the_verification_looks_like_this>
